# CI/CD

**CI uses submodules.** Workflows already pass `submodules: recursive`; if you add a new workflow that builds, do the same.

## Shared build definitions

The per-OS app build is defined ONCE and called from both its per-push and its release workflow, so a build fix lands in one place: `.github/workflows/app-macos.yml` (release.yml, for both the release and the `build:notarized` PR build), `app-windows.yml` (windows-build.yml + release.yml), `app-linux.yml` (build.yml's `linux-app-arm64` + release.yml's arm64 packaging). Under them, `.github/actions/bootstrap` is the composite action every build job runs after checkout: apply the TailscaleKit patch series, materialize the symlinks Windows checkouts mangle, set up Go from the submodule's `go.mod`, and produce (or restore from cache) `libtailscale.a` for the target — `host`, `macos-universal`, `windows-amd64` or `windows-arm64`, staging the Windows ones as both `libtailscale.a` and `tailscale.lib`. It deliberately does NOT own the checkout (a local action can only be resolved once the repo is on disk) or `git config core.symlinks` (must precede the checkout).

Rules when touching any of this:

- **Rotating `.build` caches are SAVED ONLY FROM MAIN, and restored everywhere.** A cache saved by a branch run is scoped to that branch — main and sibling branches cannot restore it — yet its ~500 MB generation spends the repo's shared 10 GB budget. When every branch saved on every push (Aug 2026), the budget sat permanently over-full and LRU eviction deleted the main-scoped caches within minutes of each save; the observed result was zero cache hits repo-wide and the full swift-cross-ui/swift-winui dependency compile (~23 min on Windows) repaid by every single run. Branch runs restore main's caches via the `restore-keys` prefix and skip saving. Two corollaries, both shipped as bugs: the save KEY must hash the same bytes the restore key hashed — SwiftPM 6.3 rewrites the committed lockfiles mid-job (format churn), so the Linux jobs discard that rewrite before saving and `app-windows.yml` discards it in its resolve step — and the save and restore `path:` lists must be IDENTICAL, `!`-exclusions included, because the path list is hashed into the cache entry's VERSION and an entry saved under one list is invisible to a restore using another. The version split's fingerprint: one job whose restore logs "Cache not found" for a key whose save then logs "Unable to reserve cache … another job may be creating this cache". Either mismatch is a cache that silently does nothing while looking healthy.
- **Caches are keyed on the matrix/arch dimension.** `libtailscale.a`, `Apps/windows/.build` and `Apps/linux/.build` all carry `runner.arch` (or the equivalent input) in their keys. An x64 object tree restored into an arm64 build is a bug this repo has already shipped once.
- **`use_cache` / `cache` is POLICY, not convenience.** CI passes true; every release workflow passes FALSE, so a shipped artifact is compiled from source on the runner that ships it. Sharing one definition is not sharing one policy.
- **`windows-build.yml`'s `paths:` list must contain every input to any of its jobs** — including `.github/workflows/app-windows.yml` and `.github/actions/bootstrap/**`, since the build steps live there now. That list has been holed twice, and both times the symptom was a branch full of green checks while the last real Windows result was a failure several commits back.

## Pitfalls

- **`lint` fails with a violation that names no file.** The `lint` job's reporter is `github-actions-logging`, which puts the path in GitHub *annotation metadata* — the log API strips it, so the failure reads as a bare "Function should have 5 parameters or less" with nothing to grep for. Don't guess at it by eye; SwiftLint's own parser disagrees with hand-written scanners in exactly the cases that matter. On macOS, `make lint-tools && make lint` reproduces CI exactly — it fetches the same `portable_swiftlint.zip` artifact the job installs. On Linux there is no such artifact, so build the real thing (`git clone --branch "$(make -s print-swiftlint-version)" https://github.com/realm/SwiftLint && swift build -c release`) and run it as CI does: `LD_LIBRARY_PATH=/opt/swift/usr/lib swiftlint lint --baseline .swiftlint-baseline.json --strict --quiet` — the `LD_LIBRARY_PATH` is not optional on Linux (without it, it dies in `Loading libsourcekitdInProc.so failed`). Check `origin/main` in a worktree at the same time: a violation that reproduces there is one an earlier merge shipped, not one you wrote. That has happened — a PR merged on a green that predated its own conflict resolution left `main` red for three merges before anyone chased it.

- **A local `make lint` that disagrees with CI is the VERSION, until proven otherwise.** The pin (`SWIFTLINT_VERSION` in the Makefile) is asserted by the `lint` target, so this now announces itself instead of arriving as four mystery violations — but the underlying reason is worth knowing, because it is not obvious that a linter version can unfreeze a baseline: the baseline records each frozen violation's `reason` STRING, so a release that merely *rewords* a rule's message stops matching and the violation comes back. 0.63 and 0.65 word `redundant_nil_coalescing` differently, which is exactly how this was found. `make lint-tools` is the fix; `TAILSCREEN_SWIFTLINT_ANY=1` is the deliberate override, and belongs only in the commit that bumps the pin (the new version has to run once against the old baseline to write the new one).

- **Adding a package dependency to `Apps/linux` breaks CI in a leg you did not touch.** The app's system libraries are listed in **three** places that must move together: the `linux-app` job in `build.yml`, the shared `app-linux.yml` (which is `linux-app-arm64` AND the release packaging), and `Apps/linux/packaging/README.md`. Miss the first two and the C shim of whatever you added fails at its own `#include` — `pipewire/pipewire.h` was the last one — long before anything links. Miss the third and the tarball ships a binary whose `DT_NEEDED` names a library the user does not have. **A local build cannot catch any of this**, because a dev machine that worked on the dependency already has its headers installed; that is exactly how it reaches CI. Check whether the new dependency is also a RUNTIME one while you are there: the AppImage picks those up from `DT_NEEDED` via linuxdeploy, the tarball does not.
- **A new macOS workflow that builds the app dies in `emit-module` with "'opus.h' file not found".** Two things are needed, and doing only the first is the trap: `brew install opus`, AND `/opt/homebrew/lib/pkgconfig` on `PKG_CONFIG_PATH`, because SwiftPM on Apple-silicon runners does not search Homebrew's pkgconfig dir and OpusKit's `pkgConfig: "opus"` therefore finds nothing. Set it as job-level `env` alongside the TailscaleKit dir the way `build.yml` does — an `export PKG_CONFIG_PATH=…/Packages/TailscaleKit` inside a run step SHADOWS the brew path rather than adding to it, so the install alone still fails. `soak.yml` was in exactly that state and failed nineteen consecutive nightlies (last green 2026-07-17) about 20 seconds in, before a single soak case ran. Note that `app-macos.yml` does NOT use brew for this — it builds a static universal libopus from source on purpose, so a shipped `.app` carries no Homebrew dylib; copy whichever of the two matches what the job is for.
- **The Windows job has a real GPU-render gate, and it needs neither a GPU nor a desktop.** `app-windows.yml`'s `Build the render self-test` / `Render self-test (WARP)` pair builds and runs `winvideo-selftest`, which renders the shared `makeColorBarsFrame()` through `CWinVideo`'s D3D11 shader to an OFFSCREEN target and reads the pixels back — so it links no WinUI and needs no window, session or package identity, and `winvideo_init`'s HARDWARE→WARP fallback means a runner with no GPU still exercises the real shader. It is the counterpart of the `linux-app` job's Xvfb + software-GL render self-test, against the SAME frame (which is why that frame lives in `TailscreenViewer` and not beside either renderer): a disagreement means the two shaders disagree about BT.709 rather than that one is broken alone. **Read the exit code before diagnosing** — 3 is wrong pixels (the `WINVIDEO_SELFTEST bar*` lines say which bar), 2 is no D3D11 device at all including no WARP, which is a runner-image regression and not a shader fault. It also passes the same `-Xcc -I$OPUS_ROOT/include/opus` / `/LIBPATH:$OPUS_ROOT/lib` the tsnet probe does, for the same reason: it imports TailscreenViewer, which depends on TailscreenAudio, which links libopus. No libtailscale `-L` though — unlike the probe it touches no transport. **It runs out of the STAGED `dist/`, and that is load-bearing.** A bare exe out of `.build` has no DLLs beside it, and hand-assembling PATH for it failed twice — first `exited 127`, then an empty log — because it needs the Swift runtime (whose arm64 PATH step is skipped on x64) and `opus.dll` (vcpkg builds libopus shared). `stage-app.sh` has already assembled the correct set in `dist/`, and `Check the app loads` proves it every run, so the step copies the exe in, runs it there, and **deletes it again before the zip and MSIX are built from that directory**. Two failure signatures worth knowing, because both read as the opposite of what they are: **127** from a step that runs a Windows exe is not "file not found" — git bash reports a PE that failed to START (typically STATUS_DLL_NOT_FOUND) that way — and an **empty** self-test log is not "no output", it means the process never ran a line of its own code, since `winvideo_init` prints and flushes on both success and failure. One more trap met on the way: `$SDKROOT` and friends are native Windows paths, and MSYS `find` cannot walk `C:\backslash\path` — it matches nothing and says nothing, so a find-then-conditionally-set-PATH block silently does nothing.
- **The arm64 tsnet probe exits 0xC0000135 with empty output, intermittently.** Seen twice on `windows-11-arm` (runs 30763286492, 30828639316), both recovered by an untouched rerun — a loader-level transient in the runner, not a staging bug. The "Check tsnet node creation returns" step in `app-windows.yml` retries once on exactly that exit code (a genuinely missing DLL fails both attempts identically, so the retry can't mask a regression). A failure that says "on both attempts" is real: diff the staging steps against a green run.
- **A leg fails to LINK a symbol nothing in it calls.** Adding a `swift test` for a package can drag the Go archive into a leg that was deliberately Go-free: a test target is an EXECUTABLE, so it links the whole dependency graph, and anything reaching TailscreenKit's `TailscreenSharer` reaches `TailscaleKit` (that target names it directly) and therefore needs `libtailscale.a`. Whether the leg calls tsnet is irrelevant. Two things follow. Set `libtailscale: host` + `go: preinstalled` on any leg that runs `swift test` over a package depending on `TailscreenSharer` — `swift build` of the same package passes without it, because a library target is compiled and never linked, which is the WASAPIKit-GUIDs failure mode wearing a different hat. And note that **you cannot reproduce this locally on a machine that has ever run `make tailscale`**: the archive is sitting in `Packages/TailscaleKit/lib/` and `libtailscale.pc` hands the linker a `-L` for it, so everything passes. To actually reproduce CI, move `Packages/TailscaleKit/lib/libtailscale.a` aside, `rm -rf` the package's `.build`, and run the test again — then put it back.

## Workflows

Four workflows under `.github/workflows/` (plus the Pages docs-deploy workflow, which since the browser viewer is also a build — see [Pages](#pages)):

### Build

Runs `make build` + `make test` on every PR and push to `main`. Skips doc-only changes. Uses `concurrency.cancel-in-progress` to drop superseded runs. Also in this workflow: **`linux-web-spike`** (a standalone job beside `linux-viewer`: bootstrap for the archive, then its OWN `actions/setup-go` step — bootstrap skips Go on a libtailscale cache hit, and this is the one job that needs Go afterwards, for the wasm build and localderp; without that step the leg was red on every cache hit — apt Node + Playwright + **Google Chrome** via `playwright install --with-deps chrome`, then `make test-web-spike` — the browser↔sharer end-to-end, see `.claude/rules/testing.md`; Chrome rather than Playwright's own Chromium because that build ships no H.264 decoder, and the decode assertions would silently downgrade to transport-only), and the **`linux-packages` matrix** — one job per leg, named `linux-protocol` / `linux-differential` / `linux-l10n` / `linux-opus` / `linux-ffmpeg` / `linux-alsa` / `linux-wasapi` / `linux-x11-capture` / `linux-portal` / `linux-notify` / `linux-xtest` / `linux-hotkey` / `linux-tailscalekit` / `linux-tsan` so the check names are unchanged, with `fail-fast: false` so one broken gate doesn't cancel the others. The legs:

- **`linux-protocol`** (Ubuntu, `swift:6.3-noble` container): `swift test --package-path Packages/TailscreenKit` — the required portability gate for the protocol package; needs the submodule + patches for the transport tier's header, apt `libopus-dev`/`pkg-config` for the `TailscreenAudio` tier, and (since `Tests/TailscreenSharerTests` landed) `go: preinstalled` + `libtailscale: host`, because the test bundle links `TailscreenSharer` → `TailscaleKit` and must resolve `tailscale_up` and friends — see the link-a-symbol-nothing-calls pitfall above; the bootstrap cache keeps the Go build off the hot path.
- **`linux-tailscalekit`** (same container + apt Go): builds the patched libtailscale c-archive and runs the TailscaleKit unit tests on Linux — the transport-portability gate.
- **`linux-tsan`** (same container, same apt/submodule/Go/libtailscale set as `linux-protocol`): `swift test --package-path Packages/TailscreenKit --sanitize=thread` — the **data-race** gate. A separate leg rather than a flag on `linux-protocol` because the two must fail separately: that one catches an Apple import in a package file, this one reads the actual memory accesses. Whole package (~31 s, 981 tests locally): the instrumented build shares no object tree with the plain one, so scoping it to the audio and sharer targets would save the tests, not the compile. **Unlike the macOS `test-tsan` job it is not `continue-on-error`** — that one runs the app target, where TSan trips over third-party C nothing in Swift can fix (libtailscale's Go runtime, ScreenCaptureKit's XPC); this package imports no Apple framework and calls no tsnet, and was clean on its first run, so a warning here is a real race. It is a real gate and was checked to be one: reintroducing `VoiceDownlink.reset`'s missing lock makes it fail with a Swift access race naming the file and line.
- **`linux-differential`** (same container + apt `golang-go make gcc libc6-dev pkg-config`, submodules for graph loading only — nothing builds or links libtailscale): `make libtailscreen`, then `swift test --package-path Packages/TailscreenDifferential` with `PKG_CONFIG_PATH=$PWD/sdk/go`. The Swift↔Go differential gate: the shipping stateful pipeline (reorder buffer, depacketizers, NACK scheduler, FEC group buffer, RR accounting) and the public Go SDK — linked in as `libtailscreen.a` through the `CTailscreen` systemLibrary — driven with identical seeded, clock-injected input, asserting identical output at every step; the stateful complement to `linux-conformance`'s vectors. Its own leg AND its own package because two Go c-archives cannot share one binary (their cgo export symbols — `crosscall2`, `_cgo_panic`, `_cgo_topofstack` — collide at link time), and TailscreenKit's test executable already links `libtailscale.a` through `TailscreenSharerTests`. Reproduce locally with `make test-differential`.
- **`linux-l10n`** (same container, *no* apt, no submodules, no Go — the package depends on Foundation and nothing else): `swift test --package-path Packages/TailscreenL10n`. Two gates in one leg. The first scans **all four** source trees — the three apps plus TailscreenHubUI — for `L("…")` call-site keys and fails on any the catalog doesn't carry; it has to run here rather than on the macOS runner, because a Linux job is the only one that sees the GTK and WinUI apps' sources on every PR, and nothing else checks their strings at all. The second covers what replaced `String(localized:bundle:)` when the catalog stopped being macOS-only: the `.strings` parser (including its recover-from-a-bad-line behaviour, since one typo from a translator must cost one string and not the language), the language-preference chain, and `%@`/`%lld` substitution with positional reordering. Not proven by it, and not provable here: that the resource bundle actually ships — that is asserted by each packaging path instead (`app-macos.yml`, `app-linux.yml`, `stage-app.sh`, the AppImage script, the Flatpak manifest all hard-fail on a missing bundle), because a missing catalog degrades silently to English rather than failing.
- **`linux-opus`** (same container + apt `libopus-dev`): builds `OpusKit` and runs its encode/decode round-trip tests — the audio-codec-portability gate for the Opus-only decision, `plans/porting-plan.md` #6.
- **`linux-ffmpeg`** (same container + apt `libavcodec-dev`): builds `FFmpegKit` and runs its H.264 decode/encode + AVCC↔Annex-B tests — the video-codec-portability gate for the Linux/Windows viewer *and* the Linux sharer's encoder.
- **`linux-x11-capture`** (same container + apt `libxcb1-dev libxcb-shm0-dev xvfb`): builds `X11CaptureKit` and runs its colour-conversion tests plus, under `xvfb-run`, live root-window capture — the screen-capture-portability gate; X11 capture is the one capture path that *can* run headlessly, which is why it landed before the ScreenCast portal.
- **`linux-alsa`** (same container + apt `libasound2-dev`): builds `ALSAKit` and runs its PCM-playback tests against ALSA's `null` device — the audio-playback-portability gate for the Linux viewer's audio output.
- **`linux-portal`** (same container + apt `libdbus-1-dev libpipewire-0.3-dev pipewire dbus`): `PortalCaptureKit`, the Wayland-capable capture path. **Named a compile/link/D-Bus-protocol/PipeWire gate and not a *portal* capture gate, because that it can never be** — the portal is defined by a consent dialog a compositor draws and a person clicks, which is precisely why X11 capture landed first with a leg that genuinely captures a screen. It runs the unit tests (Request-path derivation against hand-written strings, the portal wire constants, and that a *declined* request maps to its own case rather than an error), `portal-probe --link-check` (that libdbus and libpipewire actually LINK — a library target is compiled but never linked, the WASAPIKit-GUIDs failure mode), and `--handshake-test` / `--handshake-cancel` against a fake portal on a private bus, which cover the three portal calls plus `OpenPipeWireRemote`, the options dicts, the subscribe-before-call ordering, the `streams` parse, the restore token and an fd surviving the round trip. `dbus-run-session` is load-bearing: without a session bus those two SKIP with exit 0, i.e. the gate would pass by not running. It then starts a local `pipewire` daemon and runs `--pipewire-capture-test` / `--pipewire-format-guard` / `--pipewire-malformed-guard`, which put **real pixels** through the consumer against a synthetic producer the package owns: negotiated geometry, a *padded* `chunk->stride`, BGRA channel order, malformed buffers dropped, and the end-of-source signal (a registry event — a producer's death drops the stream to *paused*, so the obvious stream-state version never fired). Those three FAIL rather than skip without a daemon, which is why the leg has to start one. Still unproven by it: a real portal or compositor, the wireplumber autoconnect handshake (the harness links the nodes itself), and the DMA-BUF `dataType` constraint — deleting that leaves the leg green, which was checked. The leg also runs `swift test --package-path Packages/TailscreenSharerPortal` (hence the libavcodec/libopus additions to its apt list): that package's `FrameHandoff` suite is the only DETERMINISTIC test of the PipeWire-thread → encode-thread buffer hand-off, and needs neither a daemon nor a person. Everything above it in `PortalCaptureEncoder` — opening the stream, opening x264 — still has no gate anywhere and cannot have one.
- **`linux-notify`** (same container + apt `libglib2.0-dev libglib2.0-bin dbus dunst xvfb`, submodules, no Go): the two desktop-notification backends. **`WinNotifyKit` rides this leg**, which reads odd until you notice that Linux is the only place its decisions can be RUN: the shim stubs off Windows, so `swift test` + the probe cover the wrapper, the toast XML, the tag and the activation round-trip, and Windows CI is left with the link check. It is also why the leg now needs submodules — WinNotifyKit depends on TailscreenKit, whose manifest names `../TailscaleKit`, whose `Sources/` are symlinks into the submodule (nothing links `libtailscale.a`). There is no Windows counterpart to the dunst gate below and there cannot be: the notification platform is part of the OS, nothing presses a toast button from a command line, and a Windows runner has no interactive session to render one into. Then `GNotifyKit`, the Linux backend. **This one is a real gate, and the contrast with `linux-portal` is the point** — a portal is defined by a consent dialog a person clicks, while a notification daemon is an ordinary D-Bus service, so CI runs a real one (dunst, on a private `dbus-run-session` bus under Xvfb, because dunst is a drawing daemon and exits without a display) and the probe talks to it. Running `gnotify-probe` with no bus is the link check and exits 0; `--live-check` is the gate and *fails* rather than skips without a daemon. It covers the `Notify` argument signature (`(susssasa{sv}i)` — eight fields, two containers through `GVariantBuilder`; a mistake is an `InvalidArgs` error at call time), that `GetCapabilities` is read rather than assumed, `replaces_id` updating a banner in place rather than stacking one, and — the half no unit test can reach — **the signal path**: GDBus delivers to the thread-default `GMainContext` captured at subscribe time, so a notifier built on a thread that never iterates one posts perfectly and reports nothing. Withdraw → `NotificationClosed(reason=3)` and a real `dunstctl action` → `ActionInvoked` both catch that; each was verified to fail against a build with the subscriptions removed, as were the signature and the actions-dropped mutations. The daemon-readiness poll uses `ListNames` rather than introspecting the notification name, because touching that name *activates* it and races a second dunst against the backgrounded one. Not proven, and not provable here: how any of it looks — Xvfb draws to a screen nobody sees, and whether GNOME Shell renders two buttons or hides them behind a chevron is not a probe question.
- **`linux-hotkey`** (same container + apt `libx11-dev libxtst-dev xvfb`, submodules but no Go): the MUTE HOTKEY, both platforms' halves. One leg rather than two because the Windows half has almost nothing here to gate — its shim stubs out off Windows, so all Linux can check is `WinHotkeyKit`'s decisions and syntax (the real `RegisterHotKey` is run by `winhotkey-probe` on the Windows job). The X11 half is the opposite: `swift test --package-path Packages/X11HotkeyKit` covers the environment gate (a Wayland session refused even though XWayland would ACCEPT the grab and then under-deliver) and the raw-events → activations latch that stops a held chord flipping the mute at the keyboard repeat rate, and `x11-hotkey-probe --live-check` does a real `XGrabKey` on Xvfb with the chord synthesized through XTEST — then repeats it **with Num Lock on** (`XGrabKey` matches modifier state exactly, so a grab under `Ctrl|Alt` alone silently stops matching the moment a lock key joins it), then grabs the same chord from a second connection and requires the REFUSAL, which is what gates the async-error handling: `XGrabKey` reports `BadAccess` later, so a shim without the error handler + `XSync` reports success for a hotkey that can never fire.
- **`linux-wasapi`** (same container, *no* apt — the only leg with nothing to install, which is why the install step is skipped rather than run with an empty package list): `swift test --package-path Packages/WASAPIKit`. Deliberately NOT a portability gate like its neighbours — there is no WASAPI here and no null endpoint to stand in for one, so it covers only what was written to be coverable off Windows: the microphone path's mono downmix and the shim's return-code→error mapping, plus the wrapper's non-Windows syntax. The COM lifetime is left to the LINK, which is now the Windows job's `Build the app` rather than a `wasapi-probe` step of its own: the app links WASAPIKit itself, so a dedicated probe build only moved the same failure earlier — worth 112s while the app took eleven minutes to reach, not worth it once the build cache put it under two.
- **`linux-xtest`** (same container + apt `libxtst-dev xvfb`): the input-injection-portability gate for the Linux sharer's remote control — the injector's unit tests through an inject-nothing seam, `xtest-probe --audit-keysyms` checking every `X11KeyCodeMapping` row against Xlib's own tables, and `--live-check` doing real XTEST injection against Xvfb and reading the pointer back; the three cover different things and all three regress silently.
- **`linux-viewer` job** (same container + the A/V dev libs + libxcb/Xvfb + the libtailscale Go c-archive): `xvfb-run … swift test --package-path Packages/TailscreenLinuxBackends` — the platform-backend integration gate that runs `PipelineIntegrationTests` (real H.264 encode → RTP → `ViewerSession` → FFmpeg decode → collecting sinks) AND `CaptureEncoderTests` (real X11 capture → libavcodec encode → decode, through the `CaptureEncoding` seam — it needs the `xvfb-run` `$DISPLAY` or it self-skips) AND link-checks `TailscreenViewerTsnet` on Linux; a live tsnet run stays local-only. It also runs `swift test --package-path Packages/TailscreenVideoFFmpeg` — the `FFmpegCaptureEncoderBaseTests` ladder/budget/anchoring/pacing decisions — here rather than in linux-ffmpeg because that package's decoder target reaches OpusKit and this leg already installs libopus.
- **`linux-app` job** (which also caches `Apps/linux/.build` and `Apps/windows/.build` — those two swift-cross-ui compiles used to set the whole workflow's wall clock; same container + apt GTK4 / gobject-introspection / epoxy / Mesa software-GL / Xvfb): builds the native GTK desktop viewer `Apps/linux` — swift-cross-ui chrome + a downstream `GtkVideoView` hosting a `GtkGLArea` with an OpenGL BT.709 YUV→RGB renderer — and runs its headless GL YUV-readback render self-test under Xvfb, **plus the annotation-overlay self-test** (`--overlay-self-test`, on a second Xvfb with `xcompmgr`: draws a red stroke on the sharer's overlay, reads the screen back through X11 capture, and asserts the chroma — the compositor is required, since the overlay deliberately refuses to exist without one) **and the overlay-INPUT self-test** (`--overlay-input-self-test`, a third Xvfb: injects a real drag and a real Escape through XTEST at the *armed* overlay, proving the input region actually flips and that the sharer can get their desktop back — the two failures that would otherwise be a silently dead pen and a person locked behind a fullscreen window) **and the capture-backend report** (`--capture-backend-report`, which raises nothing on screen: the WIRING gate for `CaptureBackendSelection`, since its unit tests cover every branch of the decision but nothing covers whether the app feeds it the right environment. It asserts an X11 session picks X11, that no Wayland session is ever routed to X11 capture — `$DISPLAY` is set there by XWayland, so that regression is silent and sends viewers a blank screen — and that a machine with neither reports `canShare=false`. The `WAYLAND_DISPLAY`-with-no-`XDG_SESSION_TYPE` case is the load-bearing one: the explicit-session-type case returns on the first branch and cannot catch a detection-ORDER regression, while that one can, and was checked to fail against one); the live tsnet leg is local-only, see `plans/linux-viewer-gtk-plan.md`.
- **`linux-app-arm64` job** (defined in `app-linux.yml`, shared with release.yml's arm64 packaging; GitHub's free `ubuntu-24.04-arm` runner + the same multi-arch `swift:6.3-noble` container): builds the linux/arm64 libtailscale c-archive and the GTK app in release config, gates it on the same Xvfb GL render self-test, and uploads a `tailscreen-linux-arm64.tar.gz` artifact — the arm64 leg is a hard gate, not compile-only; the arm64 AppImage lives in the release workflow (aarch64 linuxdeploy/appimagetool).
- **`build-release` job** — `swift build -c release` compile check, required (release-config breaks used to surface only on published releases).
- **`release-version` job** — `scripts/test-release-version.sh` over `scripts/release-version.sh`, the tag → (version, MSIX Identity Name, MSIX Identity Version) derivation. Seconds on ubuntu, no toolchain. It exists because that derivation used to be twenty lines inline in `release.yml`, where the only way to observe its output was to publish a release — and it shipped a bug that way: a candidate and the release it precedes derived the SAME Identity Version, so Windows refused the real release as an upgrade on any machine that had installed the candidate. The suite asserts **orderings, not strings** — a release never shares an identity with its candidates, candidates ascend within their own identity, a release outranks the version before it — comparing fields numerically because `0.10.0.10` sorts under `0.10.0.2` as text and over it as a version, and Windows uses the latter. Each rule was checked to fail against a deliberate break. **The release identity is opt-in**: `app-windows.yml`'s `msix_identity` input and both PowerShell scripts default to `Tailscreen.TailscreenRC`, so only `release.yml` — passing a value that came out of this derivation — can produce a package that lands on the identity somebody's real install uses. `make-msix.ps1` still enforces the Store's trailing-zero rule, but only for that release identity; the candidate identity spends the fourth field on the candidate number, which is what keeps rc.1 → rc.2 a real in-place upgrade. The job's second step is `scripts/test-release-wiring.py`, covering the rest of the release plumbing nothing else can reach — **the job graph and the upload calls, which only ever execute on a published release**. It reads `release.yml` and asserts that no job which runs on a release `needs:` a pull_request-only job (GitHub propagates SKIPPED through `needs` unless the dependent `if` uses a status function, so that combination is silent — it skipped the macOS build on v0.10.0-rc.1 and produced a release with no `.app`, nothing red anywhere), that macos/linux/windows all still exist and all still run on a release, and that every `gh release upload` in every workflow is either in a job that checks the repo out or passes `--repo` (`gh` resolves owner/repo from the git remote, so `linux-upload` — the one job with no checkout, since it exists only to move a downloaded artifact — died with "not a git repository" *after* its 25-minute build). Both rules were written from bugs that shipped, and each was checked to fail against its own reintroduction.
- **diff-coverage gate** — `scripts/diff-coverage.sh`: lcov `DA:` records joined against `git diff -U0 origin/main...HEAD` changed lines in `Sources/*.swift`, fails under 70 % coverage of changed executable lines; currently `continue-on-error: true` with the same flip-to-required TODO convention as the `format` job.

### Screenshots

`workflow_dispatch`, plus a `pull_request` trigger scoped to its own file so edits prove themselves on their PR. Fans out to the three shared `app-*.yml` workflows with `screenshots: true` (one arch per platform — the chrome is arch-independent and x64 has the warm caches), uploading a PNG set per platform as artifacts. All three apps are launched with `--ui-preview`: a seeded, deterministic hub — signed in, the same fake peers on every platform, no tsnet node, no network — that exists for exactly this (grep `isUIPreview` / `gUIPreview`). Linux and macOS additionally carry per-state flags, spelled the same on both: `--ui-preview-video` (the in-session view) and `--ui-preview-sharing` (mid-share — the state whose clipped layout once shipped unseen), plus `--ui-preview-placard` on Linux and `--ui-preview-request` on macOS. Capture is Xvfb+ImageMagick on Linux and the runner's real desktop on Windows (`CopyFromScreen`) and macOS (`screencapture` — the hosted runner's session has the Screen Recording grant; verified 2026-08). Every capture step guards on the app process being alive first, so a crashed app fails the step rather than producing a convincing screenshot of an empty desktop.

**The macOS leg is the one the docs site publishes** (`docs/assets/screenshots/`), so it does two things the others don't. It crops with `screencapture -l <window>` rather than grabbing the whole screen, which keeps the window's own shadow on transparency instead of shipping a picture of a runner's desktop — the window id travels as an `--ui-preview-window-file` **argument**, because the step launches through `open` (which is what gets the app a real GUI session) and `open` forwards `--args` but not the environment. And it asks for a HiDPI display mode first, since hosted runners hand out a 1024x768 1x virtual display that crops too soft to publish; that step is best-effort by construction — every failure path leaves the shots at 1x rather than failing the job. Its guards come in pairs for the same reason the others have one: `pgrep` before (a crashed app must not become a convincing empty desktop) and a non-empty check after (a stale window id must not become a zero-byte PNG nobody notices until it is on the landing page).

### Soak

Nightly (`cron: 17 3 * * *`) + `workflow_dispatch`: runs `SoakTests` with `TAILSCREEN_SOAK=1` (the `ParserFuzzHarness` at ~50× PR budget plus the seeded `LossyChannel` impairment matrix). Deterministic — a red nightly names its reproducing seed/configuration.

### Screenshots

`workflow_dispatch` (plus a `pull_request` trigger scoped to its own file, so a change to it proves itself on its own PR): one job per platform through the shared `app-*.yml` workflows, each behind a `screenshots` input, uploading PNG artifacts. The Linux and macOS legs render the app's deterministic `--ui-preview*` chrome (fake sharers, one stroke per annotation tool, a seeded mid-share card — no network), Linux under Xvfb with ImageMagick and macOS on the runner's desktop cropped to the window with `screencapture -l`; the Windows leg launches the real staged app and grabs the whole screen (`CopyFromScreen`). Every capture step guards on the app process still being alive first — a crashed app must fail the step, not produce a convincing screenshot of an empty desktop. One arch per platform (x64), since the chrome is arch-independent and those legs have the warm caches.

Two macOS notes. `screencapture` needs the Screen Recording TCC grant, and a wallpaper-only PNG in the artifact is the runner saying no; the deterministic `--ui-preview` modes are what make the rest of it reproducible, so that is the layer to extend rather than reaching for pixel assertions. And the annotation seed there omits `.click` on purpose — it is an EPHEMERAL annotation and the macOS canvas sweeps it on a real timer, so unlike the GTK model (which takes the clock as an argument and can date a stroke past the shutter) it cannot survive to the capture.

### Pages

`pages.yml` deploys the docs site — root from the latest **stable** release tag, `/next/` from `main` — and, since the browser viewer, it is a build job too: it checks out submodules, sets up Go from the fork's `go.mod`, runs `make web-viewer` (the js/wasm build + gzip + `strings.json`), and publishes the page under `_site/next/view` on every run and under `_site/view` **only when** the resolved stable tag's tree carries `web/viewer/index.html` — the same channel rule as the docs, so the root never serves a page no release ships (a pre-release does not flip it). One wasm build from `main` serves both channels: unknown frames are skipped on both sides of the wire, so the newest viewer is the right one. Its `paths` filter therefore includes `web/viewer/**` and `sdk/go/**` beside `docs/**`; a change to either publishes. The published set is exactly what `publish()` in the workflow copies — `index.html`, `viewer.js`, `wire.js`, and `dist/{viewer.wasm,viewer.wasm.gz,wasm_exec.js,strings.json}` — so a new file the page loads must be added there or it 404s on the site while working locally.

### Release

Fires when a GitHub release is **published**. Cross-builds `libtailscale.a` for `arm64` + `amd64`, lipo-merges, then `swift build -c release --arch arm64 --arch x86_64` for a universal Mach-O. Wraps it in `Tailscreen.app`, codesigns with a Developer ID identity, notarizes via `notarytool`, staples, and uploads the zipped `.app` + `checksums.txt` to the release. Signing + notarization run only when **all** of the Apple secrets (`APPLE_DEVELOPER_ID_CERT_P12`, `APPLE_DEVELOPER_ID_CERT_PASSWORD`, `APPLE_NOTARY_API_KEY_P8`, `APPLE_NOTARY_API_KEY_ID`, `APPLE_NOTARY_API_ISSUER_ID`) are set; otherwise an unsigned `.app` is uploaded with a warning. The build itself lives in the shared `app-macos.yml`; it runs a **"Stamp the build"** step before compiling that rewrites `BuildInfo.commit` (`Apps/macOS/Sources/BuildInfo.swift`, the value Settings → About's Build row shows) with the short SHA, and fails the job if the `sed` didn't take rather than shipping an app that calls itself a local `dev` build. Same trick, same reason as the Windows app's stamp. The Homebrew tap repo owns cask formatting.

**One workflow, every platform.** `release.yml` fires on three triggers — release published / an on-demand PR label / `workflow_dispatch` against a tag — derives the tag, version, MSIX Identity **Name** and four-part Identity **Version** ONCE in a `version` job, and fans out to a job per deliverable: **macos** (the shared `app-macos.yml`, for BOTH the release and the `build:notarized` PR build — the latter absorbed from the retired pr-notarized-build.yml, since a signed+notarized .app is the only way to exercise UNUserNotificationCenter / TCC / Gatekeeper), **linux** (a matrix over x64/arm64 through the shared `app-linux.yml` — literally the same definition as CI's `linux-app-arm64` gate — producing an AppImage and a tarball per arch) plus **linux-upload** (a matrixed follow-on non-container job, because `gh` isn't in the swift container), and **windows** (both arches through the shared `app-windows.yml`, uploading a zip + a **self-signed** MSIX + the signing cert's public `.cer` per arch — make-msix.ps1 exports the .cer off the signed package, and docs/install.md documents the trust-once install (Import-Certificate into `Cert:\LocalMachine\TrustedPeople`); with the `TAILSCREEN_MSIX_PFX_*` secrets set every build signs with the same dev cert, so one trust covers future releases. SignPath replaces the signing step before winget submission; the manifest templates live in `Apps/windows/packaging/winget/`). The PR labels are `build-linux-package`, `build-windows-package` and `build:notarized`, each platform's jobs gate on their own, and a shared `unlabel` job removes whichever fired so re-adding it rebuilds (GitHub does not re-fire `labeled` for a label already present). There is deliberately NO `concurrency:` block: `pull_request: [labeled]` fires once per label, so adding both labels yields two runs of this workflow that each do half the work, and grouping them would let one cancel the other — the bug already fixed twice elsewhere in this repo.
