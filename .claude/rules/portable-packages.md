# Portable protocol core (TailscreenKit) and the shared packages

The rules for package files (no Apple frameworks; how to move a file in; what must be `public`) live canonically in **`Packages/TailscreenKit/README.md`** — read it before touching the package.

## The package

The wire protocol + pure decision logic (RTP/framing/control codecs, NACK/retransmit/FEC/RR loss recovery, policy/tuning types — ~110 source files across six targets, about 70 of them in the dependency-free `TailscreenProtocol` tier, which is Foundation + `Synchronization` only) lives in a standalone SwiftPM package that builds **on Linux**: `TailscreenKit`. The app consumes it as a real dependency — the files exist only in the package, and `Apps/macOS/Sources/ProtocolReexports.swift` `@_exported import`s the products so app code uses the types unqualified. Everything the app touches is `public` (incl. explicit memberwise inits); test-only seams stay `internal` and the package suites reach them via `@testable import TailscreenProtocol` / `TailscreenAudio` / `TailscreenViewer` — the sharer tier's decision surface needs no `@testable` because its extracted decision functions are `public`, so most of `TailscreenSharerTests` imports it plainly (the one exception is `SharerAskToShareCoordinatorTests`, whose reply-send seam is internal; transport has no package tests — the app suite covers it). CI's `linux-protocol` job (and `make test-protocol` locally, macOS or Linux) enforces the boundary.

## Tiers

**1. `TailscreenProtocol`** — the dependency-free base tier (Foundation + `Synchronization`). Two pixel-arithmetic types live here rather than beside a backend, because both have callers on OPPOSITE sides of the app: **`I420Converter`** (limited-range BT.709 I420 → BGRA8) serves the viewer's CPU blit and the X11 sharer's preview, and **`ThumbnailScaler`** (padded BGRA → box-averaged, channel-swapped RGBA + a once-a-second throttle) serves all three non-mac capture backends. Both are also the shape of thing that fails silently — a channel swap reads as a colour-profile problem, a stride assumption smears the image a little more with every row — so they live where Linux CI can run tests against them.

**2. `TailscreenTransport`** — `TailscalePeerDiscovery` + `TailscaleIPNWatcher` + `TailscaleAuth` (whose browser-open step is host-supplied via `onOpenAuthURL`) + `TsnetNodeFactory`, the ONE tsnet node bring-up (state dir → `Configuration` → `TailscaleNode` → optional login-URL IPN subscription with leak-safe teardown → `up()` under an explicit timeout policy). All five bring-up sites — `TsnetTransport`, the sharer, the macOS client/`AppState`, the Linux test sharer — go through it, each stating its own knobs (ephemerality, `UpTimeout`, hooks) at the call site; do not hand-roll a sixth copy. Depends on `TailscreenProtocol` and the patched `TailscaleKit`. Compiling it needs the submodule + patches (header only; *testing* the package additionally links `libtailscale.a` through the `TailscreenSharerTests` bundle — `make test-protocol` handles both), and its Combine surface (`ObservableObject`/`@Published`, which mac Foundation re-exports) compiles on Linux via `PortabilityShims.swift` — whose `Published` shim provides a `$prop.values`-compatible AsyncStream because `TailscalePeerDiscovery` consumes `watcher.$peers.values`.

**3. `TailscreenAudio`** — the voice path **both endpoints share**. The codec (`OpusVoiceEncoder` / `OpusVoiceDecoder` / `OpusPCM` — Float32↔Int16 / 960-sample framing over `OpusKit`/libopus, `@_exported`ing OpusKit so `Opus.Application` is visible), the microphone seam (`MicrophoneCapturing` + `CapturePCMConverter`, `MicrophonePipeline`, and `BlockingPCMSource`/`ThreadedMicrophone` — the capture thread, written once, because both shipped backends block and both GUI hosts service their transport from the UI thread), and the RTP ends: **`VoiceUplink`** (mic → downmix/resample → framing → Opus → RTP PT 98 → send) and **`VoiceDownlink`** (the inverse: one Opus decoder per SSRC, bounded and LRU-evicted, and **loss-resilient** — wrap-aware gap policy with Opus-PLC concealment capped + faded at the boundaries, decoder-failure cooldown, per-SSRC RFC 3550 jitter driving an adaptive `currentJitterTargetDepth`, ~1 Hz stale-SSRC sweep; PT 99 system audio deliberately skips the voice-tuned gap/jitter machinery, exactly as the mac pipeline does. Timing rides the existing calls: `ingest(_:nowNs:)` takes an optional clock — `ViewerSession` threads its `tick` clock through, hosts that pass nothing get the uptime clock), plus **`SharerVoice`** — the sharer's pairing of the two, whose SSRC is fixed rather than a parameter because viewers key their decoders on it — and **`VoiceReceiveDecisions`**, the pure loss-resilience decision layer extracted from the macOS `VoiceChannel` inbound pipeline (PT→route demux, decoder-failure cooldown gate, wrap-aware sequence-gap policy, adaptive jitter sizing, concealment cap + fade-out, stale-SSRC eviction, starve/pause discrimination), which the mac pipeline and `VoiceDownlink` both compose and Linux CI pins via `VoiceResilienceDecisionTests`.

Two more sit on top of `SharerVoice` for the sharing hosts. **`VoiceLatch`** is the mute latch itself, as a value type — `isAvailable` (a device is open) and `isOn` (you are on the air), with the four transitions allowed to move them: attach starts muted, a toggle hands back the value to write to `isMuted`, a toggle with **nothing attached moves nothing**, and a failure clears both together. Five places wrote it inline, and two of them guarded on the *uplink* while publishing the *flags*, so a device that had already failed could still be toggled into `isOn == true` — a live-microphone indicator over a device recording nothing, which is the one wrong answer a mute control can give. **`SharerVoiceSession`** composes it with `SharerVoiceRoute` and `SharerVoice` into the start/stop/toggle triple both share engines drive, and owns the ordering that is the whole of the correctness there: `inboundHandler` installed on the server before `start()` and never reassigned, the device opened late (Windows' `start()` spans tsnet bring-up and a lit mic indicator through a browser login is worse than a few dropped milliseconds), `onStopped` installed *before* `start()` (the WinUI engine installed it after), unroute before teardown, and `onStateChanged` fired only when the pair actually moved. Pinned by `VoiceLatchTests` and `SharerVoiceSessionTests`.

One type per direction rather than one per endpoint: a sharer's voice and a viewer's voice are the same stream in opposite directions, differing only in the SSRC they carry — and writing it twice would be writing the mute latch twice. Three decisions worth knowing:

- **Audio is withheld until an SSRC is assigned** — an unassigned viewer stream would go out as SSRC 0, the sharer's own reserved voice SSRC, which the sharer's anti-spoof gate then drops.
- **Nothing is delivered after `ThreadedMicrophone.stop()` returns**, which is why the running flag is read *and* `onPCM` invoked under one lock — the obvious check-then-call version loses a race a few instructions wide, and the test for it is a timing assertion because a test that races for the window passes every time against the bug.
- **A device glitch reaches `MicrophonePipeline.noteDiscontinuity()`**, which resets the resampler's carried neighbour and deliberately *not* the framer's carry, since those are samples somebody actually said.

Depends on Foundation + OpusKit + `TailscreenProtocol` (the edge points AT the dependency-free tier, which is what keeps that tier dependency-free) — it also builds on Linux, so a non-macOS client reuses the exact codec while supplying its own platform audio I/O (`VoiceChannel`/`SystemAudioTap` are the mac-side consumers; `ALSAMicrophoneSource` and `WASAPIMicrophoneSource` are the two `BlockingPCMSource` adapters, each ~40 lines and both reporting `channelCount: 1` whatever the hardware is — see the double-downmix note on `MicrophoneCapturing.onPCM`). The `linux-protocol` job installs `libopus-dev` + `pkg-config` for it (opus.pc is on Linux's default pkg-config path).

**4. `TailscreenViewer`** — `ViewerSession` + the `VideoDecoding` / `VideoSink` / `AudioSink` protocols and the `DecodedVideoFrame` value type, plus `ViewerPipeline` (the host-supplied-factory assembler that wires a decoder + sinks into a session) and `FrameStore` (the lock + value-type-COW frame hand-off any renderer backend polls from its UI thread), plus the two pieces every GUI host needs between the session and its device: `ThreadedAudioSink`, which turns a backend's blocking `play` into a non-blocking enqueue drained on one thread — mandatory when the transport is serviced by the UI thread, as it is in both the GTK and WinUI viewers — and `MonoPCMConverter`, the 48 kHz mono → device-(rate, channels) Float32 adaptation with a buffer-boundary-continuous linear resampler. `I420Converter`'s **frame-shaped overload** sits here — a forwarder onto the plane API in tier 1, present because `DecodedVideoFrame` belongs to this tier and the arithmetic does not — and `FrameRateCounter` — the stats HUD's ~1 s fps window — joined them when the Windows viewer needed the same counting the GTK sink had inline; extracting it is what surfaced that its `0` window-start sentinel collides with a legitimate timestamp. **`makeColorBarsFrame()`** made the same trip for the same reason: the 256×64 four-bar I420 test frame started beside the GTK renderer and moved here once the Windows render self-test needed to assert against the SAME pixels, which is the whole point of it — a disagreement then means the GL and D3D11 shaders disagree about BT.709 rather than that they were fed different input. Read its doc comment before writing a self-test against it: only bars 0 and 1 are exact (white/black); bars 2 and 3 are mid-luma maximum-chroma colours that land at rgb(255,63,130) and rgb(130,103,255), NOT saturated red and blue, so an assertion must use relative predicates and never exact values with a tolerance — the first Windows attempt did the latter and would have failed a correct render by 47 on one channel.

This is the portable, host-agnostic viewer data-plane core: it turns inbound RTP datagrams + a host-supplied clock into decoded video frames, decoded audio, and outbound feedback control bytes (HELLO / NACK / PLI / receiver reports), reusing `TailscreenProtocol` (`MultiCodecDepacketizer`, `NACKScheduler`, `RRAccounting`, `AudioRTPDepacketizer`, `ScreenShareControlMessage`) and `TailscreenAudio` (`OpusVoiceDecoder`). It owns **no** socket, thread, or timer — the host feeds it bytes (`receiveRTP`) and a clock (`tick(nowNs:)`) and ships its outputs — so it's fully unit-testable and portable, and it stays free of any concrete codec/renderer/audio backend (FFmpeg decode / GTK-GL render / ALSA audio plug in behind the protocols in the Linux viewer). Depends on `TailscreenProtocol` + `TailscreenAudio` only, so it also builds on Linux; the video path + audio path + HELLO/PLI/NACK/RR handshake + **FEC ingest** are covered. FEC ingest mirrors the mac client: `FECGroupBuffer` + `FECCodec.recover` arm on the first `0x0D` parity datagram, recovered packets feed the shared ingest path (RR counts them received, `NACKScheduler.noteRecovered` clears the gap without an RTT sample), NACK tolerances loosen in place while parity flows and disarm after `TransportTuning.fecParityIdleNs`, and the RR's `fecRecovered` field carries the raw-loss signal. `ViewerSession.ingestVideo` now drains all ready AUs after each ingest (`MultiCodecDepacketizer.drainReady`) so a gap fill — reorder completion or an FEC-recovered tail packet with no trailing traffic — surfaces every unblocked frame immediately. The consecutive-decode-failure **escalation ladder** (`DecodeRecovery.swift`: the `DecodeRecoveryAction` rungs, 5/30/90/300 thresholds, and the pure latched decision) lives here too, shared by all three hosts: macOS's `VideoDecoder` applies it internally (VT-session rebuild on `.recreateSession`; its adapter never reports per-frame failures to the session, so mac cannot double-ladder), while `ViewerSession` applies it for decoders that report through `VideoDecoding.onDecodeFailure` — opt-in via `onDecoderResetNeeded`/`onDecodeFatal` (both nil = the historical flat one-PLI-per-failure path, pinned by tests), which the GTK and WinUI hosts install through `TsnetTransport.run` (`FFmpegVideoDecoder.reset()` + their existing failure surfaces). Tests: `TailscreenViewerTests`.

**5. `TailscreenSharer`** — the host-agnostic *sharer* data plane, i.e. `TailscaleScreenShareServer` itself. Despite being — at the time it moved in — the biggest file in the repo and reading as deeply macOS-bound, it turned out to contain exactly **two** genuine Apple API usages (an `NSImage` preview callback and one `SCStreamError`); the rest was portable logic — viewer admission + the access-policy gate, RTP fan-out, NACK/retransmit/FEC, the congestion and per-viewer fairness controllers, the idle sweep, the capture-restart budget + hung-backend watchdog, the remote-control grant gate — that merely lived in a mac target. Moving it needed no redesign: the `os` locks became `Synchronization.Mutex`, the preview callback became opaque `Data` (the host decodes at the point of display), and the `SCStreamError.userStopped` signal became `TailscaleScreenShareServer.userStoppedErrorDomain`. The pure decision layer has since been split into sibling files as `extension TailscaleScreenShareServer` blocks — `SharerDecisions.swift` (admission/roster/helper decisions), `CongestionControl.swift` (loss attribution, fairness, bitrate/fps arms), `AdaptiveFEC.swift` (the `fec*` cluster), `RTPFanOut.swift` (packet-shaping statics) — same type, same access levels, same signatures, so the decision suites and every caller are untouched; `TailscaleScreenShareServer.swift` keeps the stateful machinery (lifecycle, capture supervision, control channel, receive loop, sweeps, fan-out, teardown).

The platform surface is two protocols in `SharerBackends.swift`: **`CaptureEncoding`** (capture + encode — callbacks for access units / parameter sets / system audio / preview / exit, commands for `requestKeyframe` / `setBitrate` / `setFrameInterval` / `setAudioEnabled`) and **`InputInjecting`** (remote-control injection). `CaptureEncoding` is deliberately shaped like `CaptureHelperWire`'s `OutType`/`InType`: the seam already existed as an IPC wire and had simply never been named as a portability boundary, which is why `HelperScreenCapture` and `RemoteControlInjector` conform with *empty* extensions (`Apps/macOS/Sources/ScreenShareBackends.swift`). The server takes a capture **factory**, not an instance, because macOS restart semantics require a brand-new helper process each time. That factory is swappable (`changeSource(filterData:captureFactory:)`) because retargeting a live share is not one mechanism on every host: the macOS helper re-resolves the selection from `filterData`, while the Windows and portal backends close over an already-picked target so a crash-restart does not re-prompt — which means only a new factory can point them somewhere else. One behaviour genuinely changed: `ScreenShareCaps.remoteControl` is now advertised **iff** the host supplied an `InputInjecting` backend — the mac-only server could hard-code "this platform can inject" and a portable one can't, so a host without injection correctly withholds the bit instead of inviting requests it can't serve.

The tier also carries **`SharerSessionCore`** — the bookkeeping a share ENGINE needs around the server, as a **value type** so the two hosts can hold it under whatever guards them. `LinuxShareSession` keeps one as an actor-isolated property, `WindowsShareSession` keeps one behind `NSLock`, and that difference is deliberate (see `.claude/rules/linux.md`), so what is shared is the state machine and not the session. Two concerns, both previously written twice and both silent when wrong: the **share-generation stamp** plus the grant high-water mark layered on it (`beginShare` / `endShare` / `isCurrentShare` / `shouldApplyGrant` / `clearGrantHistory` — PR #244's fix, and `shouldApplyGrant`'s doc comment is where the "both guards, not either" argument lives), and the **held-invite queue** (`noteInvite` / `drainInvites`), which holds an accepted ask's IP only while there is no server to tell — the GTK engine held unconditionally, so an invitee to one share got a free pass through the next share's approval gate. Pinned by `SharerSessionCoreTests`, and each host's wiring onto it by `LinuxShareSessionTests` / `WindowsShareSessionTests`.

The tier also carries **`SharerAskToShareCoordinator`** — the sharer's whole ask-to-share flow (the long-lived idempotent-per-node control listener, the `ShareRequestInbox` record/prune, and the answer sequencing: reply on the arrival connection; accept ⇒ pre-approve, then start), previously written three times, line-for-line, in the GTK engine, the Windows app and macOS `AppState`. Hosts supply closures for the parts that are theirs (`onPreApproveViewer`, `onStartShare`, the prompt surface via `onRequestsChanged`); `.claude/rules/protocol.md`'s pitfall section documents why each owned rule is load-bearing.

**6. `TailscreenViewerTsnet`** — the viewer's tsnet transport (`TsnetTransport` + `ViewerBackChannel`): node bring-up including the interactive browser-login URL off the IPN bus, peer discovery, the UDP media socket, the TCP back-channel, and the run loop that drives `ViewerPipeline`. It lived in `Packages/TailscreenLinuxBackends` until the Windows app needed it; nothing in it was ever Linux-specific, and the `import TailscreenViewerCore` that tied it to FFmpeg and ALSA referenced **no symbol** from that module. Consuming the transport therefore no longer means also acquiring a video decoder and an audio backend a host may implement differently — which is the whole point on Windows, where neither FFmpeg nor ALSA applies. Like `TailscreenTransport` it needs only the patched libtailscale **header** to compile; `libtailscale.a` is a link-time input, so the `-L` flag belongs on the executable that links it. `@MainActor`-isolated: both GUI hosts service its tick/drain loop and every sink call on the main thread. The **socket read is not on that actor** — a `Task.detached` reads `recv` and hands datagrams over through the bounded `DatagramInbox`, which the loop drains synchronously. That detachment is load-bearing and easy to undo by accident: a plain `Task { }` here inherits the MainActor, which put the read back on the loop's own executor and measured 15.6 datagrams/s on the Windows viewer against a stream sending several hundred — the whole stream overflowing the socket buffer, every frame torn, a blank window and a healthy-looking wire. If you touch that task, keep it `detached` and re-read the comment above it.

## Migrated test suites

The package's `TailscreenProtocolTests` target carries the pure suites — the loss-recovery/RTP/wire/util/decision tests whose subject types live entirely in `TailscreenProtocol` or `TailscreenAudio`. There are around sixty; **`ls Packages/TailscreenKit/Tests/TailscreenProtocolTests/` is the list**, and it is deliberately not copied here, because a hand-maintained roster of sixty filenames is wrong within a week and a stale one is worse than none — this file carried twenty-four of them for months while the directory grew past fifty. For a curated view of which suites reach through which test-only seam, and which package a new suite belongs in, invoke the **`test-catalog`** skill.

Six suites carry design rationale that does not fit in the test file itself:

- `VoicePathTests` covers the voice path end to end through fakes: the capture thread's delivery, error-vs-asked-for-stop and stop-waits-for-an-in-flight-delivery legs; the uplink's withhold-without-an-SSRC, mute-on-the-wire and SSRC-change-restarts-the-stream legs; the downlink's per-SSRC decode, bound and stalest-first eviction — the last asserted per stream, because a bound that holds while the policy evicts whoever is talking is a green check over a broken call — plus the downlink's loss-resilience legs (Opus-PLC concealment up to the cap with the capped gap faded out and the resume faded in, a late original dropped after its gap was concealed, a too-large gap resyncing, the decoder cooldown gating and recovering with the baseline kept, idle-SSRC eviction, and the jitter target adapting up under deviation and decaying when calm), all driven on an explicit `nowNs` clock so the time-based decisions are deterministic.

- `AnnotationGeometryTests` covers `AnnotationGeometry`, the **shared** derivation of a stroke's outline from its stored anchor+current points (rectangle corners, ellipse arc, arrowhead barbs, click ring). It lives in the portable tier on purpose: both endpoints render each other's relayed strokes, so the constants (`arrowHeadLength` = mac's `max(12, width*4)`, `arrowHeadAngle` = ±150°, the `ClickMarker` radii) must agree or the same `.arrow` looks different depending on who drew it. All three platforms consume it: the macOS overlay directly (`Apps/macOS/Sources/AnnotationCanvasView.swift` — its old inline copy of the formulas is gone), and the GTK and WinUI apps through the portable `AnnotationStore` (viewer strokes) and `AnnotationRasterizer` (sharer overlays), which both derive their outlines from it.
- `SharerNoticeTests` covers `SharerNoticeDecision` — *when* to interrupt the sharer, and about whom. Forget-on-leave over whole-list snapshots: an identity absent from the current snapshot is pruned so a peer that genuinely asks again is announced again, while a snapshot re-emitted for an unrelated reason — a hostname resolving off the netmap, another row changing — announces nothing. `identity` stays an opaque string because the callers legitimately want different keys: IP for control requests (a redialing peer mints a fresh connection id and would notify on each), `ip:port` for the roster (a real rejoin *should* ping). Portable because macOS had grown **three** ad-hoc mechanisms for one decision — `notifiedViewerIDs`, `controlRequestNotificationDecision`, and a bare snapshot diff in `handlePendingViewersChanged` — while Linux and Windows had none; macOS's four paths (those three plus request-to-share) and the GTK backend now all call `noticesToPost` + `noticesToWithdraw`, and what stays host-side is only the *key* each projects, pinned by `RemoteControlPolicyTests`' `noticeCandidates` tests. Also pinned here: `blocksSomeone` (which drives each platform's break-through-Focus level) implies actionable; `dismiss` is never an offered button, since closing a banner must not read as a decision about a peer; `NoticeAction`'s raw values are the **action keys** hosts put in a button's identifier slot, so a localized label in that slot (which works in English and drops every press elsewhere) is a test failure; `SharerNotice.id` round-trips through `decodeID` for every kind including colon-heavy IPv6 identities, because a press comes back as that string and nothing else; and `playsSound` is false for the whole share, since a notification ding is played by the daemon and rides out with shared system audio. `SharerNoticeTextTests` sits beside it for the freedesktop *wording* (the no-`actions` and no-`body` degradations), and pins that `SharerNoticeText.approveKey`/`denyKey` are the same strings as `NoticeAction`'s raw values — they are derived from them, because the way back from either backend is `NoticeAction(rawValue:)` and two literals for one key would drift silently.
- `PortableMuteHotkeyTests` covers `PortableMuteHotkey` — the mute-hotkey CONTROLLER both swift-cross-ui apps used to write themselves, now one type over a `GlobalHotkeyBinding` / `GlobalHotkeyHolding` pair the platform shims conform to (`X11Hotkey`, `WindowsHotkey`; the conformances live in those packages so neither app needs `@retroactive`). What is left in each app is one `hold` method: the X11 one takes the `X11HotkeySupport` session-type pre-flight and the auto-repeat warning, the Windows one is a call to `RegisterHotKey`. Driven a tick at a time through a fake binding, so the rules that used to be untested anywhere are pinned without an X server or a 50 ms sleep: the chord is held **only while there is a microphone to mute** (a global grab is exclusive), the hold decision is acted on only when it CHANGES (re-taking it on Windows destroys and rebuilds the shim's pump thread), a failure is reported and mirrored **once** rather than per tick, a retarget is announced (starting a share while watching silently moves which mic the chord flips), activations stop routing the moment the target is gone, and `chordHint` is nil unless the chord is genuinely held — that last one was a real fix, since both copies derived it from `unavailability == nil`, which is also true before any acquisition has been attempted.
- `ShortcutCatalogTests` covers `ShortcutCatalog` — every keyboard shortcut as data, meant to be rendered natively per host. Today's actual consumers are narrower than the design: the GTK and WinUI apps read only the `.toggleMicrophone` entry (through the shared `PortableMuteHotkey`), and the macOS menu/cheat-sheet render their own lists — a `GtkShortcutsWindow` / `KeyboardAccelerator` adoption is still open. Modifiers are named by ROLE — `primary` is ⌘ on macOS and Ctrl elsewhere — which is deliberately *not* `KeyModifiers`: that type is the remote-control wire model and names physical keys because it replays keystrokes on another machine, where the same physical key is what must survive; this one names intent, which is a different physical key per platform. `collisions(_:)` is checked per display style because `primary` and `control` are distinct on macOS and both collapse to Ctrl elsewhere, so a pair that reads fine in the menu bar can silently become one chord on GTK/WinUI — a third test constructs a clash so the detector can't pass by always returning empty.
- `ViewerApprovalPreferenceTests` covers `ViewerApprovalPreference` — the "Require approval for new viewers" value the GTK and Windows apps push into `setRequireApproval`: default-on, the tri-state `object(forKey:)` migration that tells a never-touched install from an explicit opt-out, the exactly-`"1"` `TAILSCREEN_OPEN_DOOR` override, and that the override never clobbers the stored choice. Portable because the server's own gate defaults **off** — right for a headless automation sharer, wrong for every app with a person in front of it — so each host has to assert the safe value, and a wrong answer here is silent: the share works perfectly and admits strangers.

`AccountProfileStoreTests` covers `AccountProfileStore` — the multi-account registry the **Linux and Windows apps share**. A profile IS a tsnet state directory; the platform part is an injected `AccountProfileLayout` (`.xdg()` / `.windowsLocalAppData()`), which is what lets Linux CI test the Windows layout. It carries one migration knob, `seedStatePath`, used by Windows only: it makes the first seeded profile adopt a pre-existing STATE DIRECTORY that sits outside the `profiles/` subtree (Windows' `%LOCALAPPDATA%\Tailscreen\tailscale`, so introducing accounts signs nobody out — adopted unconditionally, so a first run that never logged in and the run after it agree, and so a corrupt registry re-seeds onto the login still on disk instead of orphaning it). The type is neither `ObservableObject` (the stand-in this module ships on Linux is a different protocol from the identically-named one swift-cross-ui hosts observe, so each host owns the reactive wrapper — the mutators return whether they changed anything for exactly that) nor `Sendable` (one unlocked JSON file, kept inside one `@MainActor` model by strict checking). The macOS app keeps its own UserDefaults-backed `ProfileStore`/`TailscreenProfile`, and the reason is **not** that the names would collide through `ProtocolReexports`'s `@_exported import` — that is a rename, not an obstacle. `AccountProfile` is `{id, name, statePath}`; `TailscreenProfile` is those plus `loginName`, `profilePicURL` and `tailnetName`, and the last two are load-bearing in the account menu (the avatar, and the tailnet qualifier that disambiguates one GitHub identity used across several orgs, where `loginName` is identical on every one). Adopting the portable store on macOS means widening it to a superset it has no other consumer for, plus a UserDefaults→JSON migration on installs that are signed in — so the deferral is about what would be lost and moved, and converging is real work rather than a rename nobody got to.

The package's `TailscreenSharerTests` target carries the sharer-tier suites: the decision ones (`CongestionDecisionTests`, `FECOverheadDecisionTests`, `PerViewerFairnessDecisionTests`, `HelperRestartDecisionTests`, `ViewerLifecycleDecisionTests`) — `TailscaleScreenShareServer`'s pure `public static func` decisions, consumed through a plain `import TailscreenSharer` (no `@testable`; the decision surface is deliberately public, see the README's carve-out) — plus `SharerSessionCoreTests` (also a plain import — the core's surface is public) and `SharerAskToShareCoordinatorTests`, which is the one suite here that needs `@testable`, for its internal reply-send seam.

The **Windows** share engine's suite lives in its own package rather than here: `Packages/TailscreenSharerWGC/Tests/TailscreenSharerWGCTests`. It runs on the `linux-viewer` leg, and it exists because `Apps/windows` has no test target at all — so everything that engine decided used to be covered only by Linux CI typechecking the file. `SharerSessionCore` and `SharerVoiceSession` are what let it and `LinuxShareSessionTests` assert the same contracts without unifying the two hosts' isolation models. Suites that touch mac-only symbols stay in `Apps/macOS/Tests/TailscreenTests`: anything importing an Apple framework, the `AppState`/`VideoDecoder` decision suites (the former `VoiceChannel` decision suite moved with its subject — `VoiceResilienceDecisionTests` pins the portable `VoiceReceiveDecisions`), and the impairment/fuzz cluster (`RTPLossyChannelTests`, `ParserFuzzTests`, `SoakTests`) whose shared `LossyChannel`/`ParserFuzzHarness` helpers still have mac consumers. When you add a pure suite for portable code, put it in the package target; when it mixes in a mac symbol, it stays mac-side.

## Neighbouring shared packages

- **`TailscreenHubUI`** — the hub's LOOK, shared by both swift-cross-ui apps (GTK viewer + Windows app): HubStyle tokens, the header, the screen rows and their detail panes, the login/share cards, the session placard, the over-video chrome, and the header's `PeerListFilter` menu (a Menu of Toggles — swift-cross-ui has no popover and no custom menu label, but both its backends render checked menu rows). Its `AnnotationToolbar` + `RemoteControlBar` are why the Windows viewer's drawing/control layer was mostly wiring rather than new UI. `ShareCard.secondaryStart` is the same capability-shaped optional the microphone and drawing slots use: Linux fills it with "Share a window or app…" when a portal exists, Windows passes nil because its WGC picker already offers windows beside displays — a second button there would be a second door into one room. Extracted from `Apps/linux` when the Windows app needed the same design system — SwiftCrossUI + TailscreenProtocol only, no transport type, so Linux CI typechecks it on the Windows app's behalf; see its README.
- **`TailscreenL10n`** — the string catalog all three apps read: the `.lproj` files themselves plus `L(_:)` and the resolution behind it. It is a package rather than a TailscreenKit tier because TailscreenHubUI needs it, and making the chrome depend on a tier full of RTP machinery to say "Sign in to Tailscale" would be the wrong edge. Foundation only, no other dependency. The lookup is deliberately NOT `String(localized:bundle:)` (Apple Foundation) nor `Bundle.module` (its synthesized accessor `fatalError`s when the resource bundle is absent — fatal for a lookup every label goes through, where the right answer is to render English). Its `LocalizationCatalogTests` scans all four source trees and is the only gate on the GTK and WinUI apps' strings; see its README.
- **`OpusKit`** — systemLibrary wrapper over libopus, the app's audio codec (replaced AudioToolbox AAC); see its README.
- **`FFmpegKit`** — systemLibrary wrapper over libavcodec: the portable viewer's H.264/HEVC decoder AND the Linux sharer's encoder (not used by the mac app); see its README.
- **`TailscreenVideoFFmpeg`** — libavcodec behind portable seams, one target per side: the `TailscreenVideoFFmpeg` decoder target (the portable `VideoDecoding` conformance the Linux and Windows viewers share) and the `TailscreenSharerFFmpegBase` target (`FFmpegCaptureEncoderBase`, the encode-send scaffolding the X11/WGC/portal capture backends subclass — callbacks, `StartError`, the software-encoder ladder, bitrate anchor, stop sequence, congestion levers, pacing, parameter-set emission, the source-gone failure budget). Its own package so consuming either side doesn't drag in ALSA/X11 (`Packages/TailscreenLinuxBackends`) or make `linux-protocol` need libavcodec; the base deliberately depends on FFmpegKit + `TailscreenProtocol` only (NOT `TailscreenSharer` — each backend declares the `CaptureEncoding` conformance itself), so the package's test bundle links no `libtailscale.a`. Its `FFmpegCaptureEncoderBaseTests` run on the `linux-viewer` job.

## Pitfalls

- **Linux CI (`linux-protocol`) fails after touching a package file** — you added an Apple-only dependency to a file in `Packages/TailscreenKit/Sources/`. Keep package files Foundation-only (see the package README's whitelist) or move the mac-bound piece into the app target. Reproduce with `make test-protocol` (works on macOS too).
- **App fails to compile against a package type** ("initializer is inaccessible", "cannot find X in scope") — the declaration is `internal` in TailscreenKit. Mark what the app needs `public` (structs the app constructs need explicit public inits — Swift never synthesizes memberwise inits as public). Test-only seams should stay internal; tests use `@testable import TailscreenProtocol`/`TailscreenTransport`.

The Linux/Windows roadmap this enables (viewer first, then sharer) lives in `plans/porting-plan.md`.
