# Windows app and backends

## Layout

- **`Apps/windows/`** — swift-cross-ui on WinUI: sign-in/peer-list/`TailscreenHubUI`, libavcodec video into a WinUI `Image` via `CWinVideo`'s D3D11 YUV→RGB shader, WASAPI audio, sharing via WGC picker + `TailscreenSharerWGC`.
- **`Packages/WGCCaptureKit/`** — C++/raw-WinRT over `Windows.Graphics.Capture`, picker + per-window model (macOS `SCContentSharingPicker`'s analogue, unlike DXGI Duplication's whole-output-only). Hands back BGRA; `BGRAToI420` converts.
- **`Packages/TailscreenSharerWGC/`** — WGC → `BGRAToI420` → libavcodec on `FFmpegCaptureEncoderBase`. Carries **no WinUI** on purpose, so Linux CI typechecks it. Also carries **`WindowsShareSession`**, the share ENGINE — **lock-guarded, not `@MainActor`** (so `beginSharing`'s tsnet bring-up stays off the UI thread; contrast Linux's `@MainActor` `LinuxShareSession` — see `.claude/rules/linux.md` for why that split is load-bearing) — with an injectable `accessStore` so `WindowsShareSessionTests` drives it headless on Linux CI (no display/capture item/node). Shares `SharerSessionCore` and `SharerVoiceSession` with the Linux engine.
- **`Packages/SendInputKit/`** — Win32 `SendInput` shim, the `InputInjecting` backend (macOS's `RemoteControlInjector` analogue). Also owns the process's DPI awareness — see pitfalls.
- **`Packages/WinOverlayKit/`** — click-through layered window fed by the portable `AnnotationRasterizer`; `UpdateLayeredWindow` needs premultiplied BGRA, so the missing piece was the rasterizer, not a drawing API. **Owns its own thread with a message pump** — annotations arrive on a network thread and an unpumped window looks hung to Windows.
- **`Packages/WASAPIKit/`** — WASAPI shared-mode render + capture (Linux's ALSAKit analogue): mono mic at the device's own rate (channel mix here, rate conversion in `MonoPCMConverter`). Nothing to install.
- **`Packages/WinHotkeyKit/`** — `RegisterHotKey` shim, system-wide hotkey. Owns its own message-pump thread — `WM_HOTKEY` is a thread message XAML's pump would swallow. Controller is the shared `PortableMuteHotkey`.
- **`Packages/WinNotifyKit/`** — `AppNotificationManager` shim, desktop notifications. C because swift-winui doesn't project this API — only the C ABI header. The press path needs one `QueryInterface` (`ts_winnotify_activation_argument`) to read the argument off an untyped `IInspectable`.

## Pitfalls

- **A Windows toast silently never appears** — three indistinguishable causes, all in `WindowsToastPayload` (TailscreenProtocol, pinned on Linux CI): unescaped `&`/`"` in a peer hostname breaks that one peer's payload; an `AppNotification.Tag` over 64 chars is refused, not truncated (post *and* later withdraw both miss); `scenario="urgent"` is Windows-11-only — on Windows 10 an unrecognized scenario is a schema violation and posts nothing. Also read at runtime, don't assume: `WindowsNotifier.init?` returns nil when `Register()` is refused (expected for the self-contained zip build, which omits the Singleton package); `AppNotificationSetting` says whether a successfully-posted toast is actually seen. A press is matched against `SharerNoticeText.action(forKey:)`, never treated as boolean — clicking the toast **body** also activates the app, carrying `openActionKey`.
- **A share silently loses remote control AND annotations** if the process isn't DPI-aware. Both gate on `WindowsCaptureRegion.resolve` matching the WGC item's size (physical pixels) against an enumerated monitor; a DPI-unaware process sees scaled dimensions, so the match silently never happens. DPI awareness is owned by **swift-winui's `WindowsAppRuntimeInitializer`** — never set it earlier yourself (`prepareProcess()` racing ahead of it caused `E_ACCESSDENIED` / a hard crash at launch). `prepareProcess()` is only for non-WinUI hosts.
- **Verify a Windows change compiles by building on Linux**: `swift build --package-path Apps/windows --product tailscreen` (with `PKG_CONFIG_PATH` set). Only `WinUIVideoView`, `NotificationActivation`, `WindowsClipboard` are Windows-bound (`#if os(Windows)` + off-Windows stub); WinUI deps are `.when(platforms: [.windows])` so SwiftPM prunes them there. `linux-app` CI runs exactly this — it's the authority on typechecking, not on linking/running.
- **Handing a swift-winui COM pointer to a C/C++ shim**: the chain is `x.thisPtr.pUnk.borrow` — nothing shorter compiles. A `WinRTClass` wraps its COM pointer in `_inner`, so `.pUnk` doesn't exist directly; `thisPtr` (the `IWinRTObject` requirement) bridges to something that does have `.pUnk`. `borrow` is a property, not a method. `thisPtr` returns a fresh reference — wrap in `withExtendedLifetime`. Avoid `IID_IUnknown` (fileprivate, unreachable) and `WinRTClass.queryInterface` (`@_spi`) — use `thisPtr` instead.
- **The Windows viewer shader's self-test** (`winvideo-selftest`, CI-only diagnostic) renders offscreen with no window/session (falls back `HARDWARE`→`WARP` so it runs on GPU-less runners). Exit codes: 0 pass, 2 no D3D11 device (runner regression), 3 wrong pixels. Assert **relative predicates**, not exact values — `ColorBars`' fixture colors aren't saturated primaries. Keep the **overlay** pass in any rewrite — the video-bars check alone would have missed both real regressions this path shipped (wrong DXGI format, double-premultiplied alpha). Renders LIMITED range on purpose (the fixture's sample values assume it); the shader's `fullRange` arm is gated separately by `ColorBarsConversionTests` on the CPU side, because macOS sharers send full-range and WGC/X11/portal send limited.
- **A mid-session message written to `AppUIState.detail` reaches nobody** — the hub isn't on screen while a session is live (the window is the video). Anything about a live session goes to `viewerNotice` (`ViewerNoticeBanner`), cleared by the first decoded frame. (Unlike the GTK viewer, this host's video surface is up from admission — no does-it-have-a-picture branch needed.)
- **The viewer's drawing or typing silently does nothing** — check gates in order: both hidden unless the sharer advertised the matching `ScreenShareCaps` bit; then drawing wins over controlling (`forwardsInput`); then the `WinUI.Image` must actually be **focused**, not just focusable, or `keyDown` never fires. Ctrl+wheel zooms, plain wheel scrolls the sharer.
- **The sharer's drawing surface is a second window, destroyed on disarm** (not toggled interactive) — `ts_overlay` is `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE` for the whole share; both bits matter, or it swallows every click on the sharer's own desktop. It's **uniform alpha**, not per-pixel — a layered window's hit-testing follows its alpha, so it's a visible scrim, not an invisible catcher. It **refuses to arm without focus** (`SetForegroundWindow` is advisory and can be silently declined) — arming without the keyboard leaves no Escape. **`WM_KILLFOCUS` ends drawing** (Alt-Tab/Windows-key can steal focus from an ordinary top-level, unlike X11's override-redirect overlay). The release callback fires on the surface's **own pump thread** — hop before disarming, or destroying it deadlocks. `SharerDrawingLatch`/`SharerDrawingSurfacePlan` (TailscreenProtocol) own arm/disarm for both hosts.
- **Changing source mid-share can silently drop remote control** — both control and annotations gate on `WindowsCaptureRegion.resolve` finding the target's rect (a window has none once you switch display→window). The injector re-reads `WindowsShareSession.liveRegion` live (never a captured constant) and **drops** events rather than misplacing them on nil — but the grant must also be **revoked with a reason**, since a viewer whose clicks are silently dropped otherwise just sees a frozen pointer. The `ScreenShareCaps` bit itself stays advertised (static "this platform can inject," can't be withdrawn from admitted viewers mid-session).
- **A Win32 window created off the app's UI thread never appears** — it belongs to the thread that created it, and a Swift concurrency executor thread doesn't pump messages (Windows treats it as hung; 5s cross-thread call timeouts, destroyed outright if the thread exits). `WinOverlayKit` owns a message-pump thread for this — do the same for any new window.
