# Linux app and backends

## Layout

- **`Apps/linux/`** — the runnable native LINUX app (sharer + viewer): a swift-cross-ui/GTK4 app reusing `TailscreenLinuxBackends` + the shared Tsnet transport + the shared `TailscreenHubUI` chrome, with a GtkGLArea YUV renderer, and a click-through `CGtkOverlay` window that renders viewers' annotations on the sharer's own screen (see pitfalls below). Package `tailscreen-linux`, exe `tailscreen`. Sources: `{TailscreenViewerGtk,CGtkVideo,CGtkOverlay,CGtk4Sys,tailscreen}/`; `packaging/` holds AppImage / tarball / flatpak / homebrew.
- **`Packages/TailscreenLinuxBackends/`** — Linux platform BACKENDS: a library package wiring FFmpegKit+ALSAKit into the `ViewerSession` core, and X11CaptureKit+FFmpegKit into the sharer's `CaptureEncoding` seam. A Package, not an App, because it ships no runnable product the user launches — `Apps/linux` consumes it. The tsnet transport is **not** here — see `TailscreenViewerTsnet` in `Packages/TailscreenKit`. Also carries the headless test-sharer / sharer / viewer-probe executables used by the local E2E scripts. Sources: `{TailscreenViewerCore,TailscreenSharerLinux}/`; `Tests/TailscreenViewerCoreTests/` is the real-decode pipeline test.
- **`Packages/X11CaptureKit/`** — C shim over libxcb + MIT-SHM: the Linux sharer's screen capture + BGRA→I420 (limited-range BT.709); see its README.
- **`Packages/PortalCaptureKit/`** — C shim over xdg-desktop-portal ScreenCast (libdbus) + PipeWire: the WAYLAND-capable Linux capture path, and the only one that can share a single window or app. **NOT yet wired into `Apps/linux` and there is no `CaptureEncoding` conformance yet.** Its CI leg (`linux-portal`) now runs the PipeWire half for real — a local `pipewire` daemon plus the package's own synthetic producer, asserting geometry, the *padded* stride, BGRA channel order and the end-of-source signal — but it is still not a *portal* capture gate and can never be one, because the portal is defined by a consent dialog a person clicks: no frame here has come from a real compositor. Hands back BGRA and converts nothing — the portable `BGRAToI420` owns colour, same split as WGCCaptureKit → TailscreenSharerWGC. Read its README's "What is proven" table before trusting any of it.
- **`Packages/ALSAKit/`** — systemLibrary wrapper over libasound (ALSA): the Linux viewer's audio PLAYBACK backend and the sharer's microphone CAPTURE one. The two halves differ in one load-bearing way: the player DICTATES its format (output always has 48 kHz mono to play, and `default` is a plug chain), while the recorder NEGOTIATES — asking a stereo-only mic for one channel via `snd_pcm_set_params` is -EINVAL at open, i.e. "no microphone" when the truth is "a stereo microphone". It reports the rate it actually got and leaves resampling to the portable `CapturePCMConverter` (Linux-only; wired via `Packages/TailscreenLinuxBackends`); see its README.
- **`Packages/XTestInjectKit/`** — C shim over X11's XTEST + the Swift injector: the LINUX sharer's `InputInjecting` backend, i.e. what SendInputKit is on Windows. The C part exists for a different reason than CSendInput's: nothing in Xlib is unrepresentable in Swift, but `XTestFakeKey` takes a KEYCODE (this machine's keymap, meaningless off-host) while the wire carries HID usages — so `X11KeyCodeMapping` does HID→KEYSYM in the portable tier and only the `XKeysymToKeycode` hop needs a live Display. `xtest-probe` is the link check, the keysym audit, and the live Xvfb injection gate.

## Pitfalls

- **On Linux, viewers are never offered Request Control** — this X server has no **XTEST** extension. It is an *optional* X11 extension: without it every `XTestFake*` call succeeds and injects nothing, so a sharer that assumed it was there would grant control to a viewer whose every click silently vanishes. `XTestInjector.isTrusted()` therefore probes for it at open, and both hosts withhold `ScreenShareCaps.remoteControl` when it is absent. Three traps if you extend this: X11 has **no wheel** (a scroll is a press/release of button 4/5/6/7 per notch — `X11PointerMapping.scroll` owns the clamp that stops a peer's absurd delta becoming a million synthetic clicks); Xlib **queues client-side**, so a batch that is never `XFlush`ed is a click that never happens, and that is the single most likely way for the path to look broken while every unit test passes; and X11 button numbers are 1/2/3 with **middle as 2**, the opposite pairing to the wire enum's order. Also note the headless `tailscreen-sharer-linux` defaults control **off** and needs `--allow-control` — an unattended process shouldn't invite a peer to take the pointer merely because it can. `xtest-probe --live-check` is the CI gate for the whole path (real injection against Xvfb, pointer read back), and `--audit-keysyms` checks every row of `X11KeyCodeMapping` against Xlib's own tables, which catches a typo'd constant that lands on an unassigned keysym — one key that silently does nothing.
- **On Linux, the sharer's own drawing takes the whole screen, and Escape is the only way back.** Arming a tool swaps the overlay's empty input region for a full one, so it stops being click-through — which is the feature, and also means the hub window with the "stop drawing" button is now *underneath* a fullscreen override-redirect window. A window manager never focuses an override-redirect window, so Escape only works because the overlay takes focus itself with `XSetInputFocus`; `ts_gtk_overlay_set_interactive` verifies that with `XGetInputFocus` and **refuses to arm** if it did not take, because the alternative is somebody locked out of their own desktop. Two more traps: `GtkGestureDrag` reports OFFSETS from the press, not positions, so a stroke drawn from them alone lands in the top-left corner every time; and teardown must disarm before dropping the overlay, or the desktop stays unclickable for as long as the reference takes to die. `tailscreen --overlay-input-self-test` is the gate — it injects a real drag and a real Escape through XTEST, and has been checked to fail on all four (no region flip, unrebased offsets, Escape swallowed, focus never taken).
- **On Linux, a share silently loses annotations** — the session has no compositing manager. The sharer's overlay (`Apps/linux/Sources/CGtkOverlay`) is an ARGB window, and on uncomposited X11 there is no per-pixel alpha: the parts we leave transparent paint as opaque black, so the "overlay" would be a black rectangle over the sharer's whole screen. `ts_gtk_overlay_supported()` therefore returns 0 there and `SharerModel` withholds `ScreenShareCaps.annotations`, so viewers correctly grey out their drawing tools — the visible symptom is a disabled toolbar, not a covered desktop, and stderr says why. Two related traps if you extend it: GTK4 has **neither** window placement (`gtk_window_move` is gone) **nor** keep-above, so the window opts out of the window manager entirely via X11 override-redirect and reasserts position + `XRaiseWindow` on every show; and click-through is `gdk_surface_set_input_region()` with an *empty* region, applied on realize (before map) — miss it and the overlay eats every click on the sharer's desktop. `tailscreen --overlay-self-test` is the gate for all of this, and it is a real one: it has been checked to fail both with the overlay displaced 300 px and with no compositor.
- **Every ScreenCast portal call times out with no error anywhere** — you subscribed to the `Response` signal after making the call. Portal methods return *immediately* with an object path and the real answer arrives later as an `org.freedesktop.portal.Request::Response` signal on it, so the client has to **derive that path itself** (from its own unique bus name plus the `handle_token` it chose) and have the match rule in place *before* calling. Nothing errors; you just wait forever. `ts_portal_request_path` owns the derivation, `PortalRequestPathTests` pins it against hand-written strings, and `portal-probe --handshake-test` fails on it — verified by breaking the derivation deliberately, which also showed that the spec's "adopt the handle the portal returned" fallback does **not** rescue it, since subscribing to the adopted path loses the same race. Three more traps in that path, all silent: PipeWire will negotiate RGBx/YUY2/NV12 if you offer them and the buffer then is not what `BGRAToI420` expects (swapped channels, not an error); leaving `SPA_PARAM_BUFFERS_dataType` unconstrained gets you a DMA-BUF stream that connects, runs, and delivers nothing but `NULL` data pointers on any GPU compositor; and `chunk->stride` is routinely wider than `width * 4`, so reading at `width * 4` smears the image diagonally. Also: `pw_context_connect_fd` **takes** the fd and closes it, and the session handle comes back from `CreateSession` as a string but must be sent onward as an object path.
