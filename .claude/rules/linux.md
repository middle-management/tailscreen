# Linux app and backends

## Layout

- **`Apps/linux/`** — the runnable native LINUX app (sharer + viewer): a swift-cross-ui/GTK4 app reusing `TailscreenLinuxBackends` + the shared Tsnet transport + the shared `TailscreenHubUI` chrome, with a GtkGLArea YUV renderer, and a click-through `CGtkOverlay` window that renders viewers' annotations on the sharer's own screen (see pitfalls below). It offers TWO ways to start a share: "Share my screen", which picks its backend via `CaptureBackendSelection` (X11 root capture on an X11 session, the portal on Wayland), and "Share a window or app…", which is portal-only and therefore absent — not disabled — on a session with no portal. There is deliberately no window LIST in this app: the portal draws its own picker, and the compositor is the thing that knows which windows exist and which the person may see. A live portal share also offers "Change source…", which re-negotiates (a second consent dialog is inherent — picking something else is a new grant) and hands the server a replacement capture factory; declining leaves the share running, because the dialog was about a change rather than about sharing at all. Package `tailscreen-linux`, exe `tailscreen`. Sources: `{TailscreenViewerGtk,CGtkVideo,CGtkOverlay,CGtk4Sys,tailscreen}/`; `packaging/` holds AppImage / tarball / flatpak / homebrew.
- **`Packages/TailscreenLinuxBackends/`** — Linux platform BACKENDS: a library package wiring FFmpegKit+ALSAKit into the `ViewerSession` core, and X11CaptureKit+FFmpegKit into the sharer's `CaptureEncoding` seam. A Package, not an App, because it ships no runnable product the user launches — `Apps/linux` consumes it. The tsnet transport is **not** here — see `TailscreenViewerTsnet` in `Packages/TailscreenKit`. Also carries the headless test-sharer / sharer / viewer-probe executables used by the local E2E scripts. Sources: `{TailscreenViewerCore,TailscreenSharerLinux}/`; `Tests/TailscreenViewerCoreTests/` is the real-decode pipeline test.
- **`Packages/X11CaptureKit/`** — C shim over libxcb + MIT-SHM: the Linux sharer's screen capture + BGRA→I420 (limited-range BT.709); see its README.
- **`Packages/PortalCaptureKit/`** — C shim over xdg-desktop-portal ScreenCast (libdbus) + PipeWire: the WAYLAND-capable Linux capture path, and the only one that can share a single window or app. **NOT yet wired into `Apps/linux`**, though it now has a `CaptureEncoding` conformance — `Packages/TailscreenSharerPortal` — so what is left before a share can use it is backend *selection*. Its CI leg (`linux-portal`) now runs the PipeWire half for real — a local `pipewire` daemon plus the package's own synthetic producer, asserting geometry, the *padded* stride, BGRA channel order and the end-of-source signal — but it is still not a *portal* capture gate and can never be one, because the portal is defined by a consent dialog a person clicks: no frame here has come from a real compositor. Hands back BGRA and converts nothing — the portable `BGRAToI420` owns colour, same split as WGCCaptureKit → TailscreenSharerWGC. Read its README's "What is proven" table before trusting any of it.
- **`Packages/TailscreenSharerPortal/`** — the portal's `CaptureEncoding` backend: PipeWire frames → the portable `BGRAToI420` → libavcodec. The Wayland-capable counterpart of `TailscreenSharerLinux`'s `X11CaptureEncoder`, and a SEPARATE package for the same reason `TailscreenSharerWGC` is one on Windows: consuming the X11 sharer, or a viewer-only run, should not put libdbus and libpipewire on the link line. Two things in it are worth knowing before you touch it — `FrameHandoff` (the PipeWire-thread → encode-thread double buffer, whose invariant has a deterministic test) and the fact that it is constructed with an ALREADY-NEGOTIATED session, which is what stops a restart re-prompting for consent.
- **`Packages/ALSAKit/`** — systemLibrary wrapper over libasound (ALSA): the Linux viewer's audio PLAYBACK backend and the sharer's microphone CAPTURE one. The two halves differ in one load-bearing way: the player DICTATES its format (output always has 48 kHz mono to play, and `default` is a plug chain), while the recorder NEGOTIATES — asking a stereo-only mic for one channel via `snd_pcm_set_params` is -EINVAL at open, i.e. "no microphone" when the truth is "a stereo microphone". It reports the rate it actually got and leaves resampling to the portable `CapturePCMConverter` (Linux-only; wired via `Packages/TailscreenLinuxBackends`); see its README.
- **`Packages/XTestInjectKit/`** — C shim over X11's XTEST + the Swift injector: the LINUX sharer's `InputInjecting` backend, i.e. what SendInputKit is on Windows. The C part exists for a different reason than CSendInput's: nothing in Xlib is unrepresentable in Swift, but `XTestFakeKey` takes a KEYCODE (this machine's keymap, meaningless off-host) while the wire carries HID usages — so `X11KeyCodeMapping` does HID→KEYSYM in the portable tier and only the `XKeysymToKeycode` hop needs a live Display. `xtest-probe` is the link check, the keysym audit, and the live Xvfb injection gate.
- **`Packages/GNotifyKit/`** — GDBus shim over `org.freedesktop.Notifications` + the Swift wrapper: the LINUX **desktop notification** backend, i.e. what `UNUserNotificationCenter` is on macOS. The sharer surface that reaches somebody whose attention is on the thing they are sharing — during a share the app window is behind the shared content and raising it is itself visible to viewers. C only because `g_variant_new` is variadic and `Notify` takes `(susssasa{sv}i)`; every decision (what to say, when, dedupe, withdraw) is `SharerNotice` in `TailscreenProtocol`. `gnotify-probe --live-check` is the gate and is a REAL one — unlike the portal, a notification daemon is an ordinary D-Bus service, so CI runs dunst and presses a real button. See its README's "What is proven" table.
- **`Packages/X11HotkeyKit/`** — C shim over `XGrabKey` + the Swift wrapper: the LINUX **system-wide hotkey**, i.e. what WinHotkeyKit is on Windows and Carbon's `RegisterEventHotKey` is on macOS. Deliberately NOT part of XTestInjectKit: that package *writes* input for the sharer's remote control, this one *reads* one chord for the local user, and a viewer-only run wants the second without linking the first. Every decision (chord → keysym + mask, the lock-key mask variants, the auto-repeat latch) is in `TailscreenProtocol`; the shim owns only a `Display *` and `XKeysymToKeycode`. `x11-hotkey-probe --live-check` is the gate; see its README.

## Pitfalls

- **On Linux, viewers are never offered Request Control** — this X server has no **XTEST** extension. It is an *optional* X11 extension: without it every `XTestFake*` call succeeds and injects nothing, so a sharer that assumed it was there would grant control to a viewer whose every click silently vanishes. `XTestInjector.isTrusted()` therefore probes for it at open, and both hosts withhold `ScreenShareCaps.remoteControl` when it is absent. Three traps if you extend this: X11 has **no wheel** (a scroll is a press/release of button 4/5/6/7 per notch — `X11PointerMapping.scroll` owns the clamp that stops a peer's absurd delta becoming a million synthetic clicks); Xlib **queues client-side**, so a batch that is never `XFlush`ed is a click that never happens, and that is the single most likely way for the path to look broken while every unit test passes; and X11 button numbers are 1/2/3 with **middle as 2**, the opposite pairing to the wire enum's order. Also note the headless `tailscreen-sharer-linux` defaults control **off** and needs `--allow-control` — an unattended process shouldn't invite a peer to take the pointer merely because it can. `xtest-probe --live-check` is the CI gate for the whole path (real injection against Xvfb, pointer read back), and `--audit-keysyms` checks every row of `X11KeyCodeMapping` against Xlib's own tables, which catches a typo'd constant that lands on an unassigned keysym — one key that silently does nothing.
- **A capability bit proves the BACKEND exists, not that the app can act on it.** The Linux sharer supplies an `X11InputInjector` whenever XTEST is present, so the server advertises `ScreenShareCaps.remoteControl` and viewers are offered Request Control — and for the whole of Phase 1.5 nothing in `Apps/linux` subscribed to `onControlRequestsChanged`. The request arrived, the sharer was never told, and the viewer sat on "requested" forever with no way for anyone to say yes. Every piece in isolation was correct; only the subscription was missing, which is why it survived a phase that was explicitly about not advertising what we cannot do. When you add a capability bit, check what CONSUMES the thing the bit invites, not just what derives it. Two more things about this path on this host specifically: the grant snapshot must go through `SharerNoticeDecision.isStale` because `SharerModel` hops `onControlGrantChanged` to the main actor and a hop can reorder (applying a stale `nil` last tells the sharer nobody is driving their machine while somebody is) — Windows applies its updates synchronously under a lock and does not need the guard; and the generation high-water mark must **reset on teardown**, since a fresh server starts its own sequence at zero and a carried-over mark makes `isStale` discard the next share's first snapshots, which is a grant that silently never appears.
- **A notification banner offers Accept for somebody who is already in.** A notice's life is tied to the thing it is about, and nothing withdraws it for you: admitting a viewer from the hub window leaves the banner on screen, where its Accept button then does nothing — or, on a host keyed by IP rather than `ip:port`, lands on whoever connects next. `SharerNoticeDecision.noticesToWithdraw` is exactly the set `noticesToPost` discards when it intersects, named so both hosts use one rule; `SharerNotifications` calls it on every roster snapshot. The same reconcile gives the joined/left pair for free — a departure IS a withdrawn arrival — which is what makes "only viewers whose arrival was announced get a departure" fall out rather than need its own bookkeeping. One ordering rule holds it together: **`notifications.stop()` runs BEFORE the rosters are cleared**, because stopping a share expels every viewer at once and reconciling against the resulting empty list would fire one "stopped watching" banner per viewer at the exact moment the sharer already decided to stop.
- **Notifications post fine and no button press ever arrives** — the notifier was built on a thread that never iterates a `GMainContext`. GDBus captures the **thread-default main context at subscribe time** and delivers signals there, so `Notify` (a synchronous call) works from anywhere while `ActionInvoked` and `NotificationClosed` reach nobody. Construct `DesktopNotifier` on the GTK main thread. Two more in the same area: a daemon that does not advertise the **`actions`** capability silently DROPS the buttons rather than failing the call, so an unchecked Accept/Deny pair renders as a sentence with no way to answer it — ask `supportsActions` and say where to answer instead; and a notice must be **withdrawn** when the thing it is about ends, because a live "someone is waiting to be let in" banner with an Accept button is actively wrong once they have been admitted from the window. `gnotify-probe --live-check` covers all three against a real dunst, and each was verified to fail against a deliberate break.
- **On Linux, a Wayland user's share looks fine and sends viewers a blank screen.** `$DISPLAY` is set on Wayland — XWayland sets it — so any "do we have a display?" gate passes there, and X11 root capture then captures the *XWayland* root: whichever X11 apps happen to be running, which on a modern desktop is often nothing. The sharer's UI says "Sharing"; viewers see black; nothing errors anywhere. That is what this app shipped until `CaptureBackendSelection` existed, and its "Wayland is not supported" message was unreachable on any Wayland desktop for exactly the same reason. The rule now: **session kind comes from `XDG_SESSION_TYPE`, falling back to `WAYLAND_DISPLAY`, and never from `DISPLAY`**, and a Wayland session with no portal REFUSES rather than falling back to the X11 capture that would "work". `tailscreen --capture-backend-report` prints the decision for the current environment and is the CI gate; its `WAYLAND_DISPLAY`-with-no-session-type case is the one that catches a detection-order regression, and was checked to fail against one.
- **On Linux, the sharer's own drawing takes the whole screen, and Escape is the only way back.** Arming a tool swaps the overlay's empty input region for a full one, so it stops being click-through — which is the feature, and also means the hub window with the "stop drawing" button is now *underneath* a fullscreen override-redirect window. A window manager never focuses an override-redirect window, so Escape only works because the overlay takes focus itself with `XSetInputFocus`; `ts_gtk_overlay_set_interactive` verifies that with `XGetInputFocus` and **refuses to arm** if it did not take, because the alternative is somebody locked out of their own desktop. Two more traps: `GtkGestureDrag` reports OFFSETS from the press, not positions, so a stroke drawn from them alone lands in the top-left corner every time; and teardown must disarm before dropping the overlay, or the desktop stays unclickable for as long as the reference takes to die. `tailscreen --overlay-input-self-test` is the gate — it injects a real drag and a real Escape through XTEST, and has been checked to fail on all four (no region flip, unrebased offsets, Escape swallowed, focus never taken).
- **The capture outline must never be shown for a share it does not actually frame.** The recording indicator rides the annotation overlay — same window, painted under the strokes — and that window is sized from the **X display**, because it is the only geometry this side reliably has. The portal returns a stream size but no position on screen, so a portal share of one window gets an overlay the size of the whole desktop. For annotations that is a pre-existing coordinate problem; for the outline it is worse in kind, because a border around the entire screen while one window is being shared states the opposite of the truth — and the outline's whole claim is "**this** is what they can see". `SharerModel.captureMatchesOverlay` therefore gates it to X11 display shares; a portal share gets no indicator rather than a wrong one. The other trap is the thickness: a border at or above half the smaller dimension fills the buffer, which paints a solid rectangle over the shared window for the whole share, so `CaptureOutline.usableThickness` clamps to leave an interior and a geometry with no room draws nothing at all. `tailscreen --outline-self-test` reads the screen back through the sharer's own capture path and asserts BOTH that the edge is orange and that the centre is untouched; both halves were checked to fail.
- **On Linux, a share silently loses annotations** — the session has no compositing manager. The sharer's overlay (`Apps/linux/Sources/CGtkOverlay`) is an ARGB window, and on uncomposited X11 there is no per-pixel alpha: the parts we leave transparent paint as opaque black, so the "overlay" would be a black rectangle over the sharer's whole screen. `ts_gtk_overlay_supported()` therefore returns 0 there and `SharerModel` withholds `ScreenShareCaps.annotations`, so viewers correctly grey out their drawing tools — the visible symptom is a disabled toolbar, not a covered desktop, and stderr says why. Two related traps if you extend it: GTK4 has **neither** window placement (`gtk_window_move` is gone) **nor** keep-above, so the window opts out of the window manager entirely via X11 override-redirect and reasserts position + `XRaiseWindow` on every show; and click-through is `gdk_surface_set_input_region()` with an *empty* region, applied on realize (before map) — miss it and the overlay eats every click on the sharer's desktop. `tailscreen --overlay-self-test` is the gate for all of this, and it is a real one: it has been checked to fail both with the overlay displaced 300 px and with no compositor.
- **Every ScreenCast portal call times out with no error anywhere** — you subscribed to the `Response` signal after making the call. Portal methods return *immediately* with an object path and the real answer arrives later as an `org.freedesktop.portal.Request::Response` signal on it, so the client has to **derive that path itself** (from its own unique bus name plus the `handle_token` it chose) and have the match rule in place *before* calling. Nothing errors; you just wait forever. `ts_portal_request_path` owns the derivation, `PortalRequestPathTests` pins it against hand-written strings, and `portal-probe --handshake-test` fails on it — verified by breaking the derivation deliberately, which also showed that the spec's "adopt the handle the portal returned" fallback does **not** rescue it, since subscribing to the adopted path loses the same race. Three more traps in that path, all silent: PipeWire will negotiate RGBx/YUY2/NV12 if you offer them and the buffer then is not what `BGRAToI420` expects (swapped channels, not an error); leaving `SPA_PARAM_BUFFERS_dataType` unconstrained gets you a DMA-BUF stream that connects, runs, and delivers nothing but `NULL` data pointers on any GPU compositor; and `chunk->stride` is routinely wider than `width * 4`, so reading at `width * 4` smears the image diagonally. Also: `pw_context_connect_fd` **takes** the fd and closes it, and the session handle comes back from `CreateSession` as a string but must be sent onward as an object path.
