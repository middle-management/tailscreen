# Linux app and backends

## Layout

- **`Apps/linux/`** — GTK4 (swift-cross-ui) sharer+viewer, package `tailscreen-linux`, exe `tailscreen`. Two share paths: "Share my screen" (`CaptureBackendSelection` picks X11 root on X11, portal on Wayland) and "Share a window or app…" (portal-only, absent — not disabled — with no portal). No window-picker list in-app: the portal draws its own. "Change source…" on a live portal share re-negotiates (a second consent dialog is inherent); declining leaves the share running.
- **`Packages/TailscreenLinuxBackends/`** — Linux backends: FFmpegKit+ALSAKit into `ViewerSession`, X11CaptureKit+FFmpegKit into the sharer's `CaptureEncoding` seam. Also carries **`LinuxShareSession`** (`TailscreenSharerLinux`), the GTK app's share ENGINE (server lifecycle, access control, drawing latch, voice, control-request inbox, link sharing via `SharerLinkSession`) — the Linux twin of Windows' `WindowsShareSession`. **This engine is `@MainActor`**, not lock-guarded (Windows' is lock-guarded, to keep tsnet bring-up off its UI thread) — see `SharerSessionCore` below for why that split doesn't leak into the shared state machine. `SharerModel` is the thin observable façade over it; the GTK overlay reaches it through `SharerOverlaySurface`.
- **`SharerSessionCore`** (TailscreenSharer) — the share-generation stamp, grant high-water mark, and held-invite queue, held here as an actor-isolated property (behind `NSLock` on Windows). One rule set, pinned once by `SharerSessionCoreTests` for both engines, deliberately not unifying the isolation models.
- **`Packages/X11CaptureKit/`** — libxcb+MIT-SHM capture, BGRA→I420 (limited-range BT.709). The GL viewer shader is range-aware where this isn't (`uFullRange` per draw from `DecodedVideoFrame.colorInfo.range`) — macOS sharers send full-range 8-bit by default.
- **`Packages/PortalCaptureKit/`** — xdg-desktop-portal ScreenCast + PipeWire, the Wayland-capable path, only one that can share a single window/app. **Not yet wired into `Apps/linux`** (backend selection remains). Its CI leg drives a real PipeWire daemon but is not a *portal* gate — no real compositor is ever involved. Converts nothing; hands back BGRA to the portable `BGRAToI420`.
- **`Packages/TailscreenSharerPortal/`** — portal's `CaptureEncoding` backend (PipeWire → `BGRAToI420` → libavcodec), a separate package so consuming the X11 sharer doesn't pull in libdbus/libpipewire. Constructed with an **already-negotiated** session — a restart doesn't re-prompt for consent. Key internal: `FrameHandoff` (PipeWire-thread → encode-thread double buffer).
- **`Packages/ALSAKit/`** — viewer playback (dictates format: 48kHz mono via the `default` plug chain) vs sharer mic capture (negotiates — a stereo-only mic asking for 1 channel is `-EINVAL` at open, i.e. looks like "no microphone"). Reports the rate it actually got; resampling is the portable `CapturePCMConverter`.
- **`Packages/XTestInjectKit/`** — XTEST shim + injector, the Linux `InputInjecting` backend. C only for `XTestFakeKey`'s KEYCODE (host-local keymap) vs the wire's HID usages — `X11KeyCodeMapping` does HID→KEYSYM portably, only the final `XKeysymToKeycode` needs a live Display. `xtest-probe` is the gate.
- **`Packages/GNotifyKit/`** — GDBus shim over `org.freedesktop.Notifications`, the desktop-notification backend. `gnotify-probe --live-check` is a real gate (runs dunst, presses a real button).
- **`Packages/X11HotkeyKit/`** — `XGrabKey` shim, system-wide hotkey (reads one chord for the local user — separate from XTestInjectKit, which writes input). Controller is the shared `PortableMuteHotkey` (TailscreenProtocol); `Apps/linux/…/MuteHotkey.swift` keeps only the X11-specific session-type pre-flight and auto-repeat warning. `x11-hotkey-probe --live-check` is the gate.

## Pitfalls

- **Viewers are never offered Request Control** when XTEST is absent (it's optional — without it every `XTestFake*` call succeeds and injects nothing). `XTestInjector.isTrusted()` probes at open; both hosts withhold `remoteControl` then. Extending this: no wheel (scroll = press/release of button 4/5/6/7 per notch, clamp in `X11PointerMapping.scroll`); Xlib queues client-side — an unflushed batch never happens; button 2 is middle (opposite the wire enum's order). Headless `tailscreen-sharer-linux` defaults control off, needs `--allow-control`. `xtest-probe --audit-keysyms` checks every `X11KeyCodeMapping` row against Xlib's tables.
- **The GTK app must not start an unrequested sign-in.** `PickerModel.Phase` is the shared `NodeBringUpPhase`; `signedOut` is the initial phase, and `main` only calls `bringUp` if `hasSavedLogin` (same test as macOS's `attemptSessionRestore`) — otherwise link-only join/share would drag in a browser login nobody asked for. A restore needing the browser again returns to the pane with the URL rather than starting a second bring-up. Bring-up failure is `failed(String)` on the phase itself, not a separate note beside `signedOut`. `gReturnToPicker` must check `transport.liveNode` before going to `.ready`, or a link-guest mid-session gets dropped to an empty screen list. Signed out, the pane and a running share are alternatives, never stacked (`showingSignedOutShare`).
- **A decode stall is not a dead session.** `ViewerUIState.noteVideoStalled` posts a `notice` (shared `ViewerNoticeBanner`) over the frozen last frame, cleared by `markVideoFlowing`. Exception: here `hasVideo` and `viewing` flip together on first frame, so a stall with *no* video ever shown is a real dead end — placard is correct there. (Windows viewer has no such case — its surface is up from admission.)
- **The viewer's wheel has two jobs, one callback.** swift-cross-ui exposes no scroll controller; wire local zoom/pan and remote-scroll forwarding both through `ViewerInputMapping.scrollDisposition` (forward while a grant is live and Ctrl isn't held). Sign flip is load-bearing: **GDK reports `dy>0` for scrolling down, the wire reads positive `deltaY` as up** — negate when forwarding. Horizontal needs no flip.
- **A capability bit only proves the backend exists, not that the app consumes it.** When XTEST is present the server advertises `remoteControl`, but nothing acted on `onControlRequestsChanged` for a whole phase. When adding a capability bit, check the consumer, not just the producer. Related ordering bugs here: grant snapshots must pass `SharerSessionCore.shouldApplyGrant`/`isCurrentShare` (a stale `nil` from a reordered main-actor hop can tell the sharer nobody's driving while someone is — Windows applies synchronously under a lock and needs no guard); the share-generation mark must reset on teardown or the next share's first snapshots get silently swallowed.
- **A notification banner can offer Accept to someone already admitted.** Nothing withdraws a notice automatically — `SharerNoticeDecision.noticesToWithdraw` / `SharerNoticeReconciler` (TailscreenProtocol) drive both hosts' `SharerNotifications`. Order matters: `notifications.stop()` runs **before** rosters are cleared, or stopping a share fires one false "stopped watching" per viewer.
- **Notifications post fine, no button press ever arrives** — GDBus delivers `ActionInvoked`/`NotificationClosed` on the **thread-default main context captured at subscribe time**; construct `DesktopNotifier` on the GTK main thread. Also: a daemon lacking the `actions` capability silently drops buttons (check `supportsActions`, degrade the text); a notice must be withdrawn when its subject ends. `gnotify-probe --live-check` covers all three.
- **A Wayland user's share sends viewers a blank screen** if X11 root capture runs under XWayland (`$DISPLAY` is set there too, capturing whatever X11 apps happen to exist — often none). Rule: session kind from `XDG_SESSION_TYPE`, falling back to `WAYLAND_DISPLAY`, **never** from `DISPLAY`; a Wayland session with no portal refuses rather than "working." Gate: `tailscreen --capture-backend-report`.
- **The sharer's own drawing overlay takes the whole screen; Escape is the only way back.** Arming swaps the click-through region for a full one, over an override-redirect window a WM never focuses — the overlay must `XSetInputFocus` itself and `ts_gtk_overlay_set_interactive` refuses to arm if that didn't take (else the desktop locks). `GtkGestureDrag` gives offsets from the press, not positions — rebase them. Teardown must disarm before dropping the overlay. Gate: `tailscreen --overlay-input-self-test`.
- **The capture outline must never frame a share it doesn't match.** It's sized from the X display, which is wrong for a portal share of one window — `SharerModel.captureMatchesOverlay` gates the outline to X11 display shares only; portal shares get none rather than a wrong one. `CaptureOutline.usableThickness` clamps so the border never fills the buffer. Gate: `tailscreen --outline-self-test`.
- **A share silently loses annotations** with no compositor — an ARGB overlay window paints transparent-as-opaque-black on uncomposited X11. `ts_gtk_overlay_supported()` returns 0 there and the engine withholds `annotations` (visible symptom: a greyed toolbar, not a black desktop). GTK4 has no window placement or keep-above, so the overlay uses X11 override-redirect and reasserts position on every show; click-through is an *empty* input region set at realize, before map. Gate: `tailscreen --overlay-self-test`.
- **Every ScreenCast portal call times out silently** if you subscribe to `Response` after making the call — the answer arrives later as a signal on a path you must derive yourself (bus name + your chosen `handle_token`) *before* calling (`ts_portal_request_path`, pinned by `PortalRequestPathTests`; adopting the portal's returned handle does not rescue a late subscribe). Other silent traps: PipeWire will negotiate RGBx/YUY2/NV12 if offered, breaking `BGRAToI420`'s assumptions; an unconstrained `SPA_PARAM_BUFFERS_dataType` can yield a DMA-BUF stream with `NULL` data pointers on GPU compositors; `chunk->stride` is routinely wider than `width*4` (reading at `width*4` smears diagonally). Also `pw_context_connect_fd` **takes and closes** the fd; the session handle from `CreateSession` is a string but must be sent onward as an object path.
